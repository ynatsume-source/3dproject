# 自作の気圧計：区切り・読み・保存状態の全面レビュー

対象は `7f4d1e3c50e29f1ecde7382219f13f19c32777d4`、`m03x_air_barometer_pot 0.1.0`。対象ソース・lab・科学側・main は変更していない。このフォルダーの診断と結果だけを作成した。

## SB-A3 / A：格子の間にあふれた水が、終了時または次の天気でなかったことになる

読みに「水が開いた管の口まで上がって、あふれた」と出た後でも、`condition: ok` のまま全量の水を返す。続けた場合には、置き直さず数値の目盛りが復活する。住民の観察と、不可逆の水の流出・器の状態が一致しないため A。形式的な質量検査と `validateResult` は通るが、実際にモデルが認めた流出を精算していない。

原因箇所は `src/science/step/barometer-pot.ts` の 120–127、145–152、172–173、193–196 行。`check()` が格子境界でだけ呼ばれ、格子内の `read()` はあふれた言葉だけを返す。終了時は `commit(endAt)` の後に端の検査がない。さらに次の区間で遅れて境界を検査すると、その要求の新しい気圧を用いるため、前のセルですでに越えた管口を見逃せる。

### 主再現：穏やかな朝の気温変化、停止はちょうど 30 秒境界

器は直接注入した架空の状態ではなく、`p16x_vessel_tar_seal` の生成ロットを `potToEquipmentParams` に渡して用意した。500 mL、管の内径 8 mm・全長 200 mm、漏れの時定数 3096 分、器の熱時定数 739 秒、目盛り 5 mm。水は 20,000 mg。開始時刻 1007 ms、気圧はずっと 1010 hPa。

気温を 28 °C から 5 分ごとに 0.25 °C 上げる（3 °C/時）。run 開始から 3 時間 17 分 29 秒に読み、1 秒後の 3 時間 17 分 30 秒に停止する。停止は開始相対の 30 秒境界そのもの。

| 項目 | 実際の返り値 |
| --- | --- |
| 読み | 「水が開いた管の口まで上がって、あふれた」 |
| 終了時の `condition` | `ok` |
| `spilledMg` / ground への放出 | 0 mg / なし |
| 戻る水 | 20,000 mg 全量 |
| 終了時の式による水位 | 0.1002437215742811 m |
| 管口の高さ | 0.1 m |
| 現在のモデルの流出式を終了状態に当てた値 | 12 mg |

12 mg は現在のコードの体積近似による比較値で、実測の流量ではない。問題は微小な数値差そのものより、あふれた後も正常な状態として保存・再使用されること。結果は `result.json.gradualWeatherTerminalSpill`。

### 続けたときの再現：あふれた後に目盛りが復活

同じ実際の器で、最初の 30 秒は 28 °C / 1010 hPa、その後は 40 °C / 1010 hPa。開始相対 17 分 28 秒に読むと「あふれた」。17 分 30 秒まで続け、次の区間の気圧を 1010.1 hPa、気温を 28 °C に変える。置き直しは行わない。

次の区間の先頭では 20 目盛り、17 分 59 秒には 19 目盛りが返り、18 分で停止しても `condition: ok`・流出 0 mg・返却 20,000 mg のまま。気圧の小さな変化で、すでに出た「あふれた」という観察が不可逆の状態に残らない。結果は `result.json.transientSpillErased`。

単純な停止・`take_out`・設備喪失でも同じ未精算を確認した（40 °C の例の開始相対 17 分 29 秒）。そのまま 17 分 31 秒まで進めれば、次の格子頭で `spilled-top`・14 mg 放出となる。これは終了時刻が違う比較なので、同一時刻の分割不一致とは呼ばない。結果は `ordinaryTerminalSpill`。

修正は、読みの有無に依存しない物理側で、前のセルの天気による管口の越境を保存し、終了時にも取りこぼさず一度だけ精算する方向。`read()` にだけ状態変更を入れると、読む頻度で水が変わる別の問題になる。セル内の軌道またはその越境を独立に評価し、置き直すまでは数値の復活を認めないことを検査に含めてほしい。

## 一致を確認できた範囲

計 14,567 要求、61 件の対照検査、34 組の完全比較。例外・非有限値・検査器の拒否は 0。対照検査の失敗も 0 だが、上の SB-A3 は別の `findings` に記録しているので「レビュー合格」の意味ではない。

- run 原点 0 / 1007 ms、漏れ 95 / 3096 分。長い管で越境しない 1 時間・6 時間の既知天気を比較した。
- 天気の区間を同じに保ち、一括・30 秒・1 時間・17 分 137 ms・737 ms に分割。完全比較した返却物・放出・状態・観察に差はなかった。6 時間の天気変更には格子外の変更も含めた。
- 同じ読みの時刻を保った分割、読みなしとの物理比較、さらに 1 時間に 360 回の追加読みでも物理の差はなかった。少なくともこの範囲で「読むだけで実物が変わる」とは認めていない。
- `stop`・`take_out`・設備喪失を 60 秒 / 60.137 秒で比較。設備喪失も区間末まで進み、保存された寸法で動いた。
- JSON 化して戻した状態、設備パラメータのキー順を逆にした状態で一致した。予約水の質量・来歴、設備 ID / 寸法、区間の連続性を変更すると、物を消費せず拒否した。
- 合成した古い `/0` は `unsupported-state-schema`、未来の `/2` と別工程の状態も拒否。現在の `/1` に過去の実運用版があると解釈した検査ではない。

通常の分割比較では管の全長を 600 mm にした受理可能な対照も用いた。主指摘の短管 200 mm は上記の実際の封じ工程の出力。両者を混同しない。
