## 2. 再利用できる制作の土台

| 対象 | 現にある動作・状態 | 拡張時に必要なもの |
|---|---|---|
| ドットの小屋 | 流木を拾う→作業台へ運ぶ→削る→部材を付ける | 設計の選択、別形状、材料の寸法・数量、使われた結果による改修 |
| 共同の桟橋 | カメマルの測量、ランタンの土台石、ラッコの柱、ドットの床板 | 一般化した依存工程、作業担当、他用途との競合・変更・中断 |
| 貝殻・石積み | 採取した品を運ぶ、見せる、並べる・積む | 個体識別、配置編集、作品の構成履歴、他者の利用・評価 |
| 畑・若木 | 固定の若木を切り、6区画を耕し、種まき・収穫 | 再生、種や収穫物の在庫、場所選択、土地利用の効果 |
| ランタンの手帖 | 根拠のある観察→制作→記録→次の判断、SVG出力 | 建築や道具へ共通化できる意図・工程・証拠の接続 |
| 身体表現 | 移動、運搬、加工、槌打ち、採取、視線、会話による中断と復帰 | 新たな操作を既存Poseへ対応させ、完了と演出を別に扱う |

根拠：[residents.ts](../../../src/robots/residents.ts#L235) の制作物、[decide / done](../../../src/robots/residents.ts#L551)、[models.tsのPose](../../../src/robots/models.ts#L9)。
資材を取りに行き、現場で時間をかけて作る見せ方は既にある。全面的な作り直しは必要ない。

### 小屋は固定された設計図

- [HUT](../../../src/robots/residents.ts#L237) はホーム脇の固定座標・向きに24メッシュを用意する。
- 内訳は柱4、上枠4、屋根材10、杭6。`stats.built` の順に見えるようになる。
- `done(place)` は18部材で「小屋完成」の日記、`decide` は24部材後に農作業へ移る。
- この2段階は屋根完成と付帯工事完了として移行できる。単一の「完成=18/24」を推測して潰さない。
- `slotStand` と `benchStand` はメッシュの世界変換から作業位置を算出する。
- `review` は離れて眺める演出で、良し悪しを判定したり設計を直したりはしない。
- 雨を防ぐ、道具を収納する、二人で作業する等の屋根・室内の機能判定はまだない。

### 桟橋には、世界へ作用する先例がある

[village / G](../../../src/robots/residents.ts#L345) は4土台、4柱、8床板の進捗を持つ。
床を張った範囲だけ `G(x,z)` が地面を高さ1.01mまで持ち上げ、住民が歩ける場所になる。
これは「作った物が移動を変える」既存の実例として再利用価値が高い。
ただし `G` は住民モジュール内の特例であり、汎用の構造物・衝突・床面サービスではない。
ドローン等の `T.ground` と共通の動的構造物台帳にもなっていない。
開始は焚き火の集まりが2回以上になった後の固定会話、場所・部材・役割もコードで決まる。
住民が必要性を評価して複数案から設計した結果ではない。

## 3. 資材の現状：採取は実在するが収支はまだ粗い

[items.ts](../../../src/robots/items.ts#L7) は `wood / shell / stone` の個体を位置付きで保持する。
`nearest → claim → take` があり、採った品は地面のリストから消える。同一セッションの取り合いを避ける土台になる。

ただし共有世界の資材台帳にするには、次を補う。

| 現状 | 新しい契約に必要なこと |
|---|---|
| `claim` は `by` を直接代入。`take` はオブジェクト参照で削除 | 世界が採取者・予約・距離・品の版を検査し、二重取得を一度だけ確定 |
| 手持ちは `'wood' / 'piece' / 'plank'` 等の種別だけ | 原料ID、寸法・量、加工結果、所有・所在、移動中の状態を保持 |
| 保存で品ID・予約者・補充時計を省略し、ロード時にIDを振り直す | 永続ID、予約の失効・再取得、再起動しても一致する在庫 |
| 加工は流木1本から次の固定部材へ変化する | 原料消費と成果物生成を同じ確定処理にし、端材・再利用を表す |
| 放棄・取り外し・解体の一般操作がない | 途中資材を回収する、現場に置く、解体材へ変える状態遷移 |

[補充設定](../../../src/robots/residents.ts#L498) は流木20分で1個・上限8、貝殻260秒・上限16、石15分・上限12。
`items.tick` は上限未満なら抽選地点へ追加する。海況や供給源と結びついた物量モデルではない。
この補充を消すと制作が枯渇し、無制限に増やすと場所が埋まるため、供給・消費・回収を同時に設計する。

[TREES / PLOTS](../../../src/robots/residents.ts#L290) は小屋脇の若木5本と畑6区画。
伐採で流木2個を作るが木の再成長はない。これは島全体の森林を切る仕組みとは別。
種は在庫から消費せず、作物は36時間で成熟、収穫は `stats.food += 4`。収穫物の受け渡し・消費はない。
住民動物の採餌も別の規則であり、表示中の生態系の獲物在庫を減らす仕組みではない。

## 4. 移動・地形と建設の接続点

[path.ts](../../../src/robots/path.ts#L8) のA*は描画非依存。コスト関数を渡す形なので再利用しやすい。
1〜4mの格子と直線化を使い、始点・終点セルは特別にコスト1とする。
経路が返ったことだけで、狭い入口・施工姿勢・資材を抱えた通行まで保証されたと扱わない。

[walkCost / move](../../../src/robots/residents.ts#L802) は海、植生の高さ、ランタンの足場経験を扱う。
陸上では `T.pushTrees` が幹との接触を補正し、行き詰まれば再探索・仕事の放棄へ進む。
建物の壁、部材置場、工事中の立入範囲、複数人の作業位置予約は扱っていない。
建築には「完成後の通路」だけでなく、「次の部材を施工できる足場」「退路」を工程ごとに検証する必要がある。
まずドットの作業台周辺だけに動的障害物・作業位置を足し、既存の島全域経路を一括交換しない。

| 接続するデータ | 現在の場所 | 抽出時の注意 |
|---|---|---|
| 地表・水深・地被 | [land.ts](../../../src/ocean/land.ts#L19) | PNG復号と補間を写真・Texture生成から分け、同じ版の値をサーバーとブラウザで使う |
| 植生・幹の障害物 | [shore.ts](../../../src/ocean/shore.ts#L245) | 描画生成時の配置から `vegH / pushTrees` が生まれる。高さだけ移せば同じ道になるわけではない |
| 桟橋の歩行床 | [residents.tsのG](../../../src/robots/residents.ts#L374) | 既存床の挙動を保持して、一般の床・支柱・壁へ順次拡張 |
| 魚を見つめる入力 | [build.tsのnearFish](../../../src/ocean/build.ts#L581) | カメラ周辺の魚モデルから取得。共有の正史へ入れる観察には世界側の根拠が別途必要 |

嘉弥真島は [locations.ts](../../../src/data/locations.ts#L388) の `far:760 / roam:720 / center:[320,-270]`。
サーバー案の半径2km拡張はこの基準コミットで実装済みではない。
地形範囲・原点・バージョンを変える作業は、永続座標・施工位置の移行を伴う。
採取・漁・建築を海まで伸ばす段階では、海の範囲は描画だけの問題でなくなる。

## 5. 最近統合されたランタンから受け継ぐこと

[lantern-study.ts](../../../src/robots/lantern-study.ts#L97) は世界入力と検証可能な意図を受け持ち、移動や描画を行わない。
実際の作業後に `residents.ts` が `complete` を呼ぶ。AIの文だけでは観察や作品が完成しない。
取り組み・途中作品・根拠・中断の関係は、建築の「案→施工→使用→改修」へ受け継げる。
ただし星の5行動専用コントローラーをそのまま全住民の万能エンジンにはしない。

このmainでは、当初の試作から次の変更が統合されている。

- 二度目の観察は45分以上待つ。待機中は石積みなど通常の暮らしへ戻る。
- 星図は二時刻の星を輪・点・点線で比較し、それぞれの観察時刻を明示する。
- 会話APIは20秒、判断は8秒の応答期限。判断は120回中最大80回、残り40回を会話用に残す。
- 根拠：[取り込み時の記録](../lantern-autonomous-study/README.md#取り込み時のレビューと変更main統合時)、[mind.ts](../../../src/robots/mind.ts#L56)、[lantern-brain.ts](../../../src/robots/lantern-brain.ts#L45)。

有効化はなお [build.ts](../../../src/ocean/build.ts#L320) の `?lantern-study` 条件付き。
保存は `seaglass.lantern-study.residents.v1`、通常の島は `seaglass.residents.v1`。
[main.ts](../../../src/main.ts#L2199) の住民時刻は試作時だけ `Date.now()`、通常はまだ観賞用の `clock.ms`。
「mainへ統合された」ことと「全訪問者の通常モードで稼働する共有機能」は同じではない。

## 6. 記憶と保存を共有の歴史へ移す

[save / load](../../../src/robots/residents.ts#L1163) は位置・手持ち・日記・関係・小屋進捗・畑・桟橋などを20秒ごとにlocalStorageへ保存する。
日記はメモリ400件、保存時300件。会話は保存時160件。Lanternも作品6・観察24・記憶48・判断32件に制限する。
これは長年の作品史の保管庫ではなく、端末内の作業用の状態である。
従来のタスク・経路・会話途中や資材予約は完全には保存されず、Lanternの途中行動も復元時は中断扱いになる。

- 共有版は作品・設計版・使用履歴・確定イベントを永続保存し、住民が思い出す短い記憶と分ける。
- 現在の `today` や日記テキストだけから資材台帳を復元しない。旧資材は移行起点の初期残高として扱う。
- ブラウザごとの既存歴史は自動で正史へ合流させない。共有開始時のスナップショットを一つ指定する。
- 切断中は最終受信状態と接続状態を表示し、ローカルで新しい建築や材料消費を確定しない。
- 過去の個人世界を残すなら、共有正史とは明示的に分けて閲覧・書き出しできるようにする。

## 7. 世界サーバー案の前提で修正が必要な点

[既存サーバー案](../ai-world-server/README.md) の方向性は今回の共有世界要求と合う。
ただし以下を実装済みの事実として見積りへ使わない。

| 案の記述 | 実コードから確認できること |
|---|---|
| `residents.ts` は描画と切り離されている | `Resident` にモデル・Mesh・Groupを持ち、構築時に材質・canvas、更新時に描画、DOM吹き出しを扱う |
| 追加は地形loaderと保存先だけ | 時計・乱数、植生衝突、AI入力、魚の観察、作業状態、イベント配信、再起動時の未完了処理も境界が要る |
| 3時間を約2秒、負荷は小さい | 既存Node試験はTHREEを生成し、DOM/storageをスタブ化した開けた丘。実島の常時運転・配信・DB・AI込みの計測ではない |
| 4体の配信は数百バイト | 位置だけと、作品・部材・資材・会話・履歴を含むデータ量は別。実payloadと同時閲覧数で検証する |
| 切断時は手元シミュレーションへ戻る | その結果を正史扱いすると同じ島が分岐する。共有版は新規確定を止める方針へ改める |
| 特定モデル名・単価・VPS費用・2〜3日の工程 | ここでは提供状況・料金・工数を検証していない。採用時に公式情報と実測で再見積りする |

Node実行の根拠は [lantern-residents-check.ts](../../../scripts/lantern-residents-check.ts#L1)。
同ファイルは `document / localStorage / Date.now / Math.random` を置換し、地形もテスト用に差し替える。
「WebGLなしで試験可能」という有用な実績であり、「描画非依存なサーバー用ロジック完成」の証明ではない。
サーバー案の末尾に残るFly.io推奨・共有可否の質問は、文中の後日の国内VPS決定と今回の回答により古い。

## 8. 少しずつ移すための実装順

1. **入力と正本の境界**：住民時計、乱数、保存、地形問い合わせを注入可能にする。旧動作を同じ条件で比較する。
2. **材料と一つの作業場所**：永続ID・予約・確定イベントを、小屋の採取→加工→設置だけで通す。既存24部材を移行fixtureにする。
3. **描画への投影**：その作業場所の状態からMeshとPoseを更新する。メッシュが設計・進捗の正本を兼ねる箇所を一つずつ減らす。
4. **使用と改修**：一つの用途で効果を判定し、使用イベントを記録。失敗・改修・解体を同じ材料契約で扱う。
5. **共有サーバーで確定**：同じ世界ロジックを単一の書き手で運転し、保存・再起動・配信を検証。ブラウザは補間と表示へ移る。
6. **AI提案を接続**：許可された材料・操作・工程へ提案を変換し、世界で検査する。失敗時は同じ工程をルールで続ける。

この順は各段階をローカルの試験世界で先に検証する意味であり、個人世界を本番仕様にする提案ではない。
具体的な共有運転の着手順と受入条件は、本提案のロードマップ・サーバー設計と揃えてレビューする。
最初から地形編集・全森林伐採・任意コード実行・全生態系のサーバー移管を同時に行う必要はない。
アニメーション・材質・海の鑑賞機能を維持しながら、創造に必要な世界状態から順に切り出す。
