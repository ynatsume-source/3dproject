## 既存の計画と揃える点

| 論点 | 本提案の扱い |
|---|---|
| 共有世界 | ユーザー確認済み。一つのサーバー正本、閲覧者は状態を受け取る |
| 国内VPS | 既存提案の決定事項を尊重。別ホスティングへの移行提案をしない |
| API費 | 月15,000円の全用途合計に含む。制作を別枠にしない。モデル/単価は配備時に確認 |
| ランタン | 統合後の45分比較、通常生活への復帰、80/120のブラウザ試作枠を現状として認識。新サーバーの費用台帳と混同しない |
| 世界時計 | 住民・材料・工事・耐久はサーバー時刻。観賞の空・過去の再生は正史を進めない |
| 島の拡張 | 現行の島＋周囲の海の拡張と競合させず、建築に使う地形の版を共有する |

## 既存サーバー案から補正したい点

1. `residents.ts` はNodeで検査できるが、Threeモデル、DOM、localStorage、経路、小屋のtransformが同居している。地形ローダーと保存先の変更だけで本番分離完了とはしない。[現状調査](CURRENT_STATE.md) を参照。
2. 切断時に各ブラウザで工事を続けると、誰もが同じ世界を見る条件を破る。共有モードは最終状態を表示し、別の個人記録を自動統合しない。
3. 屋根の作用、動的障害物、資材ID・所在・予約・加工の保存は追加が必要。建物のメッシュ生成だけで完了しない。
4. 月上限と会話の自然な終了を両立するため、場面を予約し、送達不明の課金枠を勝手に返却しない。旧バックアップ復元で費用枠を巻き戻さない。
5. 既存提案末尾のFly.io推奨・共有世界の再質問は、中段の決定事項と一致しない。本提案では国内VPS・共有の最新方針に合わせた。

## 最初にレビューしたい設計判断

- 一般化する範囲：最初は小さな部材グラフと用途3種。見た目の自由さと支持/通行検査の負荷が釣り合うか。
- 完了条件：設置部品・実機能・実利用を分け、雨の試験と実際に降った雨での経験を区別できるか。
- 主体性：候補生成の範囲が狭すぎて色違いの定型物だけにならないか。どこからグラフ編集を許すか。
- 初期の規模：25cm、32部品、長辺6m、高さ2m、1層は体格と動線を測るための候補値。採用前に確認する。
- 本人の知識：全体の利用ログが、作者の全知の記憶にならないか。知る経路を確保できるか。
- 共存：現在の採集、小屋、桟橋、石積み、会話、睡眠、ランタンの制作を消さずに接続できるか。
- 移行：新規の共有世界を始めるか、選んだ旧snapshotを取り込むか。切替直前に運用方針を確定し、閲覧者の保存を自動統合しない。
- 履歴：意味ある部品変化と作品来歴は残し、全フレームの記録を無制限に増やさない保存方針でよいか。

## 開発の引き継ぎ方

設計の用語は `CONTRACTS.md` を正とし、改訂が必要なら関連資料も同時に直す。資料に書いた数値は実測済みではない。運用・体格・負荷の検証結果で更新する。

初回実装では、完成模型を突然出現させるUIデモと、材料/動作/機能/履歴がつながる実装を区別して提示する。規則による受け入れ試験と実APIの創造性評価も別々に記録する。

Codexに任せる候補は、部材/敷地検査、運搬と施工の状態機械、利用と改修の検証、来歴UI、モデル/LOD、長期試験の観測道具。Claude側のサーバー正本・予算台帳と契約を合わせてから、それぞれ独立ブランチで進める。
