# 実装の順番と、完成を判断する基準

状態：未採択の実装計画。今回は設計資料と説明用の体験図のみを作成する。以下の機能・試験・実API評価を実装済み/通過済みとは扱わない。

## 1. 最初に届けたい体験

ドットが、経験した不便や関心から小さな共同作業場を考える。複数の敷地・部材配置から選び、材料を運んで組む。ランタンが実際に使い、本人の観察や伝えられた不便をもとに一度改修する。その場所が、次に来た閲覧者にも同じ形と履歴で残っている。

最初の例は **雨を避ける作業面＋屋根のない観測場所**。星を見る空間まで屋根で塞がない。完成画像だけでなく、材料待ち・途中の施工・使われ方・改修前後を見ることができる。

これは試験で成立させたい一周であり、本番の全住民に同じ筋書きを命令するものではない。実AIの運用では、作らない、途中でやめる、別の配置を選ぶ結果も認める。

## 2. 段階ごとの出口

| 段階 | 見られるようになるもの | 次へ進める条件 |
|---|---|---|
| D0 今回の設計 | 全体像、状態契約、体験図、作業分担 | Claudeが既存サーバー案との差分と最初の範囲をレビューできる |
| G0 世界の境界 | 描画しなくても同じ住民・時間・物の所在が保たれる | 実地形・保存・再開・操作の検査が成立 |
| G1 制作の一周 | 運ぶ→組む→使う→直す一つの作業場 | 固定条件の試験で、資材・用途・動線・改修・履歴が成立 |
| G2 共有の島 | 二人が同じ工事と作品を眺め、誰も見ていなくても続く | サーバー正本、閲覧専用配信、移行、復旧、費用台帳が成立 |
| G3 自律的な創作 | 本人の記憶・好みに応じて異なる計画が生まれる | 実APIの7日観察、その後28日の継続評価を通す |
| G4 暮らしを変える作品 | 棚・道・橋・保管・修理・共同制作 | 生態・資源・移動・役割の整合と長期維持が成立 |
| G5 島の文化 | 音の作品、図案の再利用、住民ごとの作風や場所の習慣 | 一次履歴から文化の成立経緯が追え、反復と変化を評価できる |
| G6 島の外へ | 他の場所へ移動し、素材・知識・作り方が持ち込まれる | 地域間の所在・輸送・時間・歴史が一貫し、処理量に収まる |

G1は実験用の世界で成立させる。公開の共有世界へはG2の検査後に接続する。既存のClaudeによるサーバー開発はG0の契約を合わせてG1と並行できる。G4以降のすべてが揃うまで最初の島を待たせない。

完成日を固定した巨大改修にはしない。まずG0〜G2の小さなPR群で実測し、その結果で工程を見積もる。長期の奥行きは、G3以降の数週間・数か月の観察と改良で育てる。期間が長いだけの建築待ち時間を、奥行きの代わりにはしない。

## 3. 最初の範囲を固定する

### 入れる

- 島は嘉弥真島、共有世界は一つ。実験用世界IDを別に持つ。
- 作者はまずドット。ランタンは実際の使い手、制作内容によって協力者。カメマル・ラッコは身体に合う観察や利用を行う。
- 地形・既存通路を検査した2つ以上の候補敷地。狭い指定範囲に一つの新しいWork。
- 25cm単位の建築、支柱・横材・作業面・屋根・接合部の小さなカタログ。正確な部材寸法/必要数は設計生成器で決める。
- 図面候補は複数。作業面の位置、向き、屋根と開空間の関係が異なり、雨/見通し/搬入距離の評価に差が出ること。
- 材料の永続ID・予約・持ち運び・加工・設置・回収。実在の途中状態。
- `supportSurface / rainShelter / restSeat` のうち必要な用途を検査して利用する。最初の作業場では作業面と雨よけを必須とする。
- 実利用の記録、作者へ伝わる経路、一度の改修、再起動後の保持、部品履歴の再生。
- 材料品質・耐久のフィールドと評価器境界。制御された故障条件で一部交換を検証する。

### 後続段階で広げる

- 地形の自由掘削、高層建築、全面的な剛体/流体/破壊計算。
- AIが新しいJavaScriptや部材カタログを本番で自己追加すること。
- 一度に4体全員の職人化、無制限の同時工事、材料の自動無限供給。
- 船の自作と自由航海、別島の開拓、電力網等の大きな機構。
- 種ごとの成長/腐食を実測精度で再現すること。最初は出典と限界を示した簡略規則。
- 来訪者が住民に建築を命令する、資材を送る等の介入。初期の共有は閲覧。

## 5. 最初の一周の受け入れシナリオ

### 正常な一周

1. ドットが実際の雨による作業中断、または記録された試験条件を経験する。試験条件は実天気と明記して区別する。
2. 既存小屋の代替手段も検討し、制作に意味がある候補を作る。新規建築を必ず正解にしない。
3. 2敷地×複数配置から、雨よけ・開空間・接近経路を満たす案を選ぶ。
4. 使える材料が減る。ドットが運ぶと手元の所在へ移り、加工したら部材/廃材へ分かれる。
5. 未施工の部品は効果を持たない。途中の支柱を避けて歩き、空間が足りなければ別の作業順へ進む。
6. 完成した作業面をランタンが使う。雨天作業域と星を観察する域の違いが行動に反映する。
7. 使用中の不便が発生し、作者に観察/会話として届く。作者が改修を提案し、既存部品を回収/再利用して変更する。
8. 改修前後の利用結果と、部材の変更履歴を見返せる。別の閲覧者も同じWorkを見る。

### 失敗しても世界が壊れない

| 条件 | 必要な結果 |
|---|---|
| 材料を二人が同時予約 | 一人だけが取得、もう一人は待つ/別案。収支の差分0 |
| 設置途中に材料・敷地の版が変わる | 再検査し、中断や再計画。成功した記憶を作らない |
| 通路/出入口を塞ぐ部品案 | 施工前に却下。人/生物を部材の中に閉じ込めない |
| 支柱を先に撤去する提案 | 依存構造を検査し、仮支え等を要求する |
| 睡眠/会話/電池切れで中断 | 作業進行・持ち物・仮置きが保存される |
| DB書込中に停止、同じ操作を再送 | 全体が確定済みか未確定のどちらか。同じ部品/消費は増えない |
| 閲覧者が0人/1人/複数人 | 同じ世界時間と履歴。AI呼出と資材供給を閲覧回数で増やさない |
| サーバーとの接続が切れる | 最終更新時刻つき表示。ローカルの別工事を正史に混ぜない |
| 天気API/AI APIが止まる | 不明な天候を捏造しない。規則で可能な暮らしを続ける |
| AIの遅延・架空部材・未観測事件 | 受理せず、利用可能な候補から続ける |
| 課金応答が不明・月上限に近い | 予約を保留し追加呼出を抑止。実行済みの生活作業は続ける |
| 傷んだ屋根/使われない作品 | 用途を再評価。撤去を自動強制せず、修理・放置・転用の選択余地 |
| 旧いローカル保存を再度接続 | 共有世界を初期化せず、重複移行しない |

## 6. 自発性と面白さの評価

完全な同一結果を期待する試験と、自由な創作の評価を分ける。

**世界の正しさ**は自動で検査する。資源収支差分、重複変更、未到着の成功、欠番、失われた作品、誤った機能の有効化が0であること。保存と復旧は副作用の直前/直後の両方で停止させる。

**提案の質**は同じ条件群で、規則・記憶ありAI・関連記憶を除いたAIを比較する。違う敷地や形を選ぶだけで創造性成功とは扱わない。根拠となる経験に合う判断か、使って生じた差が次の判断に効いたかを確かめる。

**人が眺めたいか**は別の評価にする。例えば一週間の記録から、着手理由・材料待ち・利用・改修・未使用を含む事例を選び、オーナーとClaudeが確認する。

- 作者らしさを行動や形から感じられるか。
- 日ごとの出来事が、前日までの経験につながっているか。
- 説明文を読まなくても「何をしているか」が見えるか。
- 同じ案の言い換え、無意味な解体再建、全員の作風の同一化が続いていないか。
- 制作・手入れが食事/睡眠/観察/会話/休息を圧迫していないか。
- 使われないものにも来歴があり、島の静けさや余白が残っているか。
- 後日、その場所や作品をもう一度見に来たいと思うか。

最初は7日、その後28日を観察単位にする。規則による高速試験は整合性を見るもので、実APIを数週間動かした証拠にはしない。数値目標は計測後に決め、初めから「必ず毎日作品を完成させる」等を報酬にしない。

## 7. 規模・描画・運用の予算

初期候補の上限は **新規Work 1件、同時施工1件、部品32個以内、敷地の長辺6m、高さ2m、地上1層**。部品数は現存施工部品の合計で、改修の旧部品・新部品・仮支えも含む。回収材・仮置き材は在庫と敷地の占有上限で別に管理する。これは設計試験用の値であり、現地の適正建築密度や計測済み性能ではない。敷地の面積・高さ・生息域・通行と合わせて検査し、部品数だけでは可否を決めない。

レンダラーは同じ部材をまとめ、遠景を簡略化する。部品は視覚IDから世界IDへ戻せるようにする。低画質で見えなくなっても、物の所在や雨よけ効果は消えない。スマートフォン/Windows ANGLEの実測で上限を調整する。

AIの創作費は既存の**全用途合計月15,000円**に含める。1体150〜200円/日の目安を全員が毎日使うと月額と両立しないので、残額と残り日数から配分する。作品一つごとの部品配置にはAPIを使わず、節目に計画・振り返りを行う。

VPS・保管・通信費はAI費と別に見積もり、契約やデプロイは既存サーバー開発の手順で扱う。今回の設計ブランチで契約・課金・本番起動は行わない。

## 8. 次に広げるときの条件

- **棚・道**：在庫所在とナビゲーションに効くことを確認してから、作者の評価に使う。
- **修理・嵐**：まず既知条件の摩耗と部品交換、その後に実天候由来の損傷へ。島が常に壊れ続ける調整にしない。
- **共同制作**：材料と作業区画の予約が成立してから、役割交渉・手伝い・断る・引き継ぐを追加する。
- **風の楽器**：音のパラメータと風への応答を世界ルールとして用意し、住民が聴いた結果を評価できるようにする。
- **文化**：図面の再利用、作者の来歴、好みの変化を保存し、利用時間だけの順位付けにしない。
- **島の外**：地域IDと所在・輸送を拡張する。遠い地域すべてを毎フレーム動かす前提にせず、重要な旅・輸送は正本に残す。

## 9. ClaudeとCodexの分担

Claudeは最新main・世界サーバー・本番の最終統合を担当。Codex側は独立した部材検査器、制作実行器、作品来歴UI、描画、検証器などを契約ごとに分けて進められる。

各作業は「基準SHA・対象契約版・触るファイル・実例・失敗例・実施した確認・残った懸念」を引き継ぐ。実装の違いが出たときは契約を直し、古い図や設計文だけを残さない。本提案をそのまま採択ADRへ移す必要はなく、採用した判断だけを既存ADR/ARCHITECTUREへ反映する。
