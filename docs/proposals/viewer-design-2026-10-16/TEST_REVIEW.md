# 試験配信・テスト週の画面レビューと、指標の基準値の取り方（2026-10-17）

`README.md`（ライブ配信を中心にした設計）の続き。試験配信（11月中旬〜、限定公開）とテスト週（11月下旬〜12月上旬）で、**見る人の側から何を、どう確かめるか**と、公開のあとに**良くなったかを判断する基準値をどう取るか**をまとめる。

- 実装・配信の操作は main（D16）。この文書は確かめ方と合格の目安だけ。
- 数値の目安は、既存の検査（`tools/layout/composition.cjs`・`tools/lab/night.cjs` など）の考え方と数字を借りたもの。実際の画面で一度測ってから見直す。
- 「要確認」は、YouTube やツールで本当に取れるかをまだ確かめていない項目。

---

実機のリハーサル（2026年11月上旬、家の PC・本物の LLM、24〜48時間）では、この A のうち見られる分を見る。あわせて、視聴者として気づけたか・どう感じたかを `REHEARSAL.md` の項目で記録する（2026-10-23）。

## A. 画面レビューの観点表

### A-0. やり方

| いつ | 何を | 誰が |
|---|---|---|
| 試験配信の初日 | 安全な範囲の撮影（README §13-1 の表）。全端末・全表示 | main が撮影、この担当が判定 |
| 試験配信の期間（毎日） | 下の5つの時間帯に、PC とスマホ縦の2枚ずつ撮る | main（自動で撮れるなら自動） |
| テスト週（7日） | 上に加えて、10分ごとに1コマを自動で保存し、同じ時刻のログ（状態の文 L2・視点 L8）と並べる | main が保存の仕組み、この担当が判定 |

**撮る時間帯**：朝の集まり（9:00ごろ）、日中（14:00ごろ）、焚き火の会（夕方）、夜（23:00ごろ、ランタン）、深夜（3:00ごろ、全員が眠っている時間を含む）。新月に近い夜を少なくとも1回含める。

**結果の残し方**：観点ごとに「合格／要調整／不合格」と、根拠の画像の名前を1行で残す。不合格は main に直してほしい内容を添えて返す。

### A-1. 文字が読めるか（HUD）

| # | 観点 | 合格の目安 |
|---|---|---|
| T1 | 状態の1行と字幕が、**スマホ横の全画面**で読める（D22：スマホ縦の小さい画面は読めなくてよい） | 画面上の文字の高さが約14px 以上（1080p で 40px、字幕 46px：`screens/README.md` §3） |
| T2 | 明るい砂浜でも、夜でも読める。ただし**世界観を優先**（D22） | 目で読めること。明るさの比は記録するが合否にしない（真昼の白い砂浜では 2〜4 になる設計：`screens/README.md` §5）。文字の下の曇りが景色を暗く見せていないか、のほうを重く見る |
| T3 | 何も触らない状態で、YouTube の表示（題名・チャンネル名・操作バー）と重ならない | 重なり 0。操作バーが出た状態では、小さい表示（AI の表記・時刻）だけなら重なってよい |
| T4 | 状態の1行の整え方（README §3-2）が効いている | 「（あと○m）」と末尾の括弧が出ていない。21字を超える文が 60px に下がり、2行を超えない |
| T5 | 縄づくりの段階の並び（README §3-6）が、作業中だけ出る | 作業場の工程でないときに出ていない。今の段階が見分けられる |

### A-3. 巡回と構図

| # | 観点 | 合格の目安 |
|---|---|---|

## B. 指標の基準値の取り方

### B-0. 考え方

- （2026-10-17 オーナー決定 D19・D20：4週間の基準の期間と、週に一度の数字の受け渡しを採用）
- 新しいチャンネルで始めるので、**比べる前の数字がない**。そこで**公開から4週間を基準の期間**とし、その間は大きな変更（巡回の長さ・HUD の中身）をしない。5週目から一度に一つずつ変えて、基準と比べる。
- 試験配信・テスト週は限定公開で、見る人がいない。ここで取るのは**止まらないか・正しく出ているか**の数字だけ（下の「守り」）。
- 個人を特定する情報は扱わない。数字はすべて合計か平均。

### B-1. 何を測るか

| 目的 | 指標 | 出どころ | 間隔 |
|---|---|---|---|
| 戻ってくる（いちばん大事） | チャンネルの月間視聴者のうち、**ライト（過去1年で1〜5か月視聴）とコア（6か月以上）**の割合。ライブ単位・動画単位の新規とリピーターは公式に取れない | YouTube Studio（チャンネル単位、期間は7日・28日・90日、1〜2日ごとに更新。API には無い） | 週（D20 でオーナーから） |
| 戻ってくる | チャンネル登録の増減（ライブから／ダイジェストから） | YouTube Analytics | 週 |
| 眺めてもらえる | ライブの同時視聴者数（時間帯ごとの平均と最大） | YouTube Analytics | 日 |
| 眺めてもらえる | ライブの平均視聴時間、ピーク同時視聴者数、チャットレート | YouTube Studio のライブの分析（配信中と終了後）。時間帯ごとの分け方は公式の API に無い（`day` と `month` だけ） | 週 |
| 眺めてもらえる | **時間帯ごとの同時視聴者数（夜がもつか）** | **自前で記録**：Data API の `liveStreamingDetails.concurrentViewers` を数分おきに読み、島の時刻とログに並べて残す（下の B-4） | 日 |
| どの視点が人を留めるか | 視点ごとの同時視聴者数の変化 | 上の自前の記録と、ログの視点の切り替え（L8）を時刻で並べる。YouTube のライブの「主なシーンでの視聴者維持率」も参考に見る | 週 |
| 忙しい人に届く | ダイジェストの視聴回数・平均視聴時間・**章ごとの離脱**（視聴者維持率のグラフ） | YouTube Studio（動画ごと、反映に1〜2日。主なシーンの表示は60秒以上・100回以上視聴の動画だけ） | 動画ごと |
| 忙しい人に届く | ダイジェストの表示回数とクリック率（題名の効き目） | YouTube Analytics | 週 |
| 読み物 | 島だよりの閲覧、ダイジェストの説明欄から島だよりへの移動 | Web の計測。説明欄のリンクに出どころの印（例：`?from=digest`）を付ける | 週 |
| 入口 | 地球の海のページ →「いまの島」カード → ライブへ移った数 | Web の計測。**地球と住人の島を区別して送る直し（10/11 の M8）が前提** | 週 |
| 参加 | チャットレート（1分あたりの書き込み数）、アンケートの参加数 | YouTube Studio のライブの分析／アンケートの結果 | 週 |
| 守り | 配信が止まった回数と時間、規則で追いついた時間 | 配信の運用の記録・ログ（L4） | 日 |
| 守り | ダイジェストの自動検査で止まった回数 | ダイジェストの仕組み | 日 |
| 守り | チャットで保留・削除した書き込みの数（管理の手間） | YouTube Studio | 週 |
| 守り | AI の費用（月の上限に対する使った割合） | 予算台帳 | 日 |

### B-4. 自前の同時視聴者数の記録（main への依頼の案）

YouTube の分析では、24時間配信を時間帯ごと・視点ごとに分けて見られない（API の時間の単位は日と月だけ。12時間を超える配信の分析がどう残るかも公式に記載なし）。そこで、自宅 PC 側で次を記録する。

- Data API の `videos.list` で `liveStreamingDetails.concurrentViewers`（いま見ている人数）を**5分おき**に読む。1回1ユニットで、1日288ユニット（既定の1日10,000ユニットに収まる）。更新の頻度は公式に記載なしなので、細かく読みすぎない。
- 読んだ値を、その時刻・島の時刻・映していた視点（L8）と一緒に、ログとは別のファイルに残す（世界のログには混ぜない。住人の AI にも渡さない）。
- 視聴者がいない・人数を非公開にしているときは値が返らない。アナリティクスの確定値とずれることがあるので、傾向を見るためだけに使う。

### B-2. 基準の期間（公開から4週間）で答えたい問い

| 週 | 問い | 次に試すこと（5週目以降、一つずつ） |
|---|---|---|
| 1〜2週 | どの時間帯に人がいるか。夜（ランタン中心）は人が残るか | 人が多いのに平均視聴時間が短い時間帯の巡回を見直す |
| 1〜4週 | どの視点・どの場面で人が増える／減るか | 人が減る視点の長さを短くする、増える場面（縄づくり、灯りなど）に寄せる動きを足す |
| 2〜4週 | ダイジェストのどの章で離脱するか | 離脱の多い章を短くする、順番を変える |
| 4週 | 戻ってきた視聴者の割合の基準値 | 以後、変更のたびにこの値と比べる |

### B-3. まとめ方

- 開始から当面は、週に一度、オーナーが YouTube Studio の数字（同時視聴者数・平均視聴時間・リピーター・登録・ダイジェストの維持率）をこの担当に渡す。この担当が B-2 の問いに沿ってまとめ、次に試すことを提案する。
- 自動でまとめる仕組み（YouTube Analytics の API など）は、認可と手間を見てから。要確認。
