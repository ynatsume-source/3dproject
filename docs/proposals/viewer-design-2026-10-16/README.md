## 3. ライブ配信の設計

### 3-1. 視点と巡回

- **視点は5つ**：付き添いドロン 01 ドット・02 ランタン・03 カメマル・04 ラッコ、巡回ドロン 13（海と浜）。**実装済みのカメラはこの5つだけ**。上空の 14 と定点の 05〜12 は未実装で、できたら巡回に加える。
- **巡回の規則（案）**

| 状況 | 動き |
|---|---|
| ふだん | 起きていて動いている住人を順に。1視点に数分（目安2〜5分、試験で決める） |
| 節目が起きた | その住人の付き添い（01〜04）か 13 へ寄せる。節目の札を出す |
| 同じ動作の繰り返し（例：殻を打つ） | 数回見せたら次の視点へ（殻を打つの扱いは下の「開始時の巡回」） |
| 朝の集まり・焚き火の会 | 会の間は会の場所に留まる（13 か、話している住人の付き添い） |
| 夜 | ランタン（02）中心。補う絵：眠っている3人を順に、13 で夜の浜と星空 |
| 視点の投票（§6） | 投票の結果は「次に寄る視点」の候補として使う。世界には影響しない |

- 巡回は表示側の都合で住人を動かさない。住人が退屈な行動に縛られないことを優先する。
- 夜の見せ方は §3-5。

#### 開始時の巡回：時間で順に回す（案、2026-10-17）

main の計画では、開始時は時間で順に回し、節目で寄せる動きはあとで足す。その間隔の案。

| 時間帯 | 回る順 | 1視点の長さ |
|---|---|---|
| 昼（起きている住人が3人以上） | ドット 01 → ラッコ 04 → カメマル 03 → ランタン 02 → 島 13。**眠っている住人は飛ばす** | 住人 **3分**、島 13 **1分30秒**（1周 約10〜13分） |
| 昼（起きている住人が1〜2人） | 起きている住人 → 島 13 | 住人 **4分**、島 13 **1分30秒** |
| 夜（起きているのがランタンだけ） | ランタン 02 → 島 13 → 眠っている住人1人（毎回替える）→ ランタン 02 … | ランタン **6分**、島 13 **2分**、眠っている住人 **1分** |
| 全員が眠っている | 島 13 → 眠っている住人を順に | 島 13 **3分**、各住人 **1分** |

- 切り替えは短いフェード（1〜1.5秒）。**話している途中では切り替えない**（発話が終わるまで最大60秒延ばす）。
- 「起きている／眠っている」は、いまの状態の文（「眠っている」）か体の状態から読む。読み方は main が決める。
- **同じ動作が続くとき（殻を打つ、1個約4分）**：最初に回ってきたときは通常の長さ（3分）で見せる。次の周でも同じ住人が同じ動作を続けていたら、その視点は **1分** に縮める。3周目以降も続いていたら、その周は飛ばす（島 13 の引きの画で作業場が映る分は残る）。撚る・縒り合わせるも同じ扱い。
- できれば最初から足したい例外（安く作れるなら）：朝の集まり・焚き火の会が始まった出来事が出たら、会が終わるまで島 13 か話している住人に留まる。
- 長さはテスト週で、時間帯ごとの平均視聴時間を見て直す。

### 3-2. 映像に焼き込む表示（HUD）

YouTube の映像は押せず、端末ごとに並べ替えもできない。横1920×1080の映像を、スマホの幅390pxに縮めても読めるようにする。

| 出すもの | 出さないもの |
|---|---|
| 視点の名前（住人の名前＋ドロン番号） | 操作ボタン、常時の詳細 |
| 状態の文1行（今と同じく実際の状態から） | 残り時間、進捗％、Next |
| 島の時刻と島暦の日付（遅延があるので「今」とは書かない） | 住人の内部の数値（報酬・信頼など）、AI の入出力 |
| 節目の札（起きたときだけ数秒） | 科学の隠れた値（強さ・キメ値など） |
| 今日の予定（朝の集まりで本人が言ったこと。§6） | |
| 「住人はAIです」の常時表記（小さく） | |

- 文字の目安：1080p で本文60px以上、1つの表示は2行まで。
- YouTube の操作バーや題名と重ならない位置に置く（**安全な範囲は要確認**）。
- 字幕：会話はルマウ語の吹き出しに日本語訳（いまの仕組みのまま）。

#### 開始時の最小構成：文言表（案、2026-10-17）

見た目（書体・配置・文字の下の曇り・島の文字・会話の字幕・節目の札）と**文字の大きさ**は `screens/README.md`（第2版、D21・D22）に置き換えた。下の表の文言と出さないものはそのまま使う。下の表の大きさ（72px など）と、明るさの比 4.5 の目安は第2版で改めた。

main の計画の最小構成（視点の名前・島の時刻・状態の1行・「住人は AI です」）に合わせた文言。節目の札・今日の予定は、最小構成のあとに足す。

| 要素 | 文言の型 | 例 | 1080p での大きさ（390px に縮めたとき） | 置き場所（案） |
|---|---|---|---|---|
| 状態の1行（**最優先**） | 状態の文をそのまま（世界が作る文） | 浜で流木を運んでいる | **72px**（約15px） | 左下 |
| 視点の名前 | 住人：`名前 ・ ドロン番号` ／ 島：`島をめぐる ・ ドロン13` | ドット ・ ドロン01 | 56px（約11px） | 状態の1行のすぐ上 |
| 島の時刻 | `島暦○年 ○月○日 ・ HH:MM` | 島暦1年 6月1日 ・ 19:42 | 48px（約10px） | 右上 |
| AI の表記（常時） | `住人はAIです ・ 映像は自動で撮影しています` | — | 40px（約8px） | 右上、時刻の下（下のモックで右下から変更） |
| 島 13 のときの1行 | `起きている：名前・名前` ／ 全員が眠っていれば `みんな眠っている` | 起きている：ランタン | 72px | 左下（状態の1行の位置） |

- **状態の1行の長さ**：72px で画面幅の8割に収まるのは約21字。いまの状態の文（`residents.ts` の `statusOf`、2026-10-17 にこの担当が数えた）は約160種類で、次の3種類が長くなる。
  - 道のりの「（あと67m）」が付く文：例「昼寝のできる静かな水面へ向かっている（あと120m）」で26字
  - 括弧の付く文：例「作業台で流木を部材に削っている（3本目）」で21字
  - 工程名をそのまま出す文：工程表の名前は最長23字（例「器にタールを塗り、竹の管を栓に通して口を封じる」）
  - 括弧を除いても20字を超えるのは「浜から水平線を見渡し、見える島を地図に記している」（24字）など数種類
- **ライブ用の整え方（案、2026-10-17 改訂）**：世界の文は変えず、表示の直前に次の順で整える。純粋な関数で、世界や AI には触れない。
  1. 道のりの「（あと○m）」を外す（ライブでは2秒ごとに変わる数字がちらつくため）
  2. 末尾の括弧のうち、**数や回数だけのもの**（「（3本目）」「（4/8）」など）を外す。言葉の括弧（「（島にはいない）」など）は意味があるので残す
  3. ~~21字を超えたら 72px → 60px に下げる~~（第2版で状態の1行は 40px になり、1行に約35字入るので不要。`screens/README.md` §3）
  4. それでも1行に収まらなければ、読点か「。」の後で2行に折り返す（切り詰めて意味を変えない）

#### 大きさの確かめ（モック、2026-10-17）

`hud-mock.html` を 1920×1080 で描き、スマホ（幅390px・3倍の画面）で見える大きさ（1170×658）に縮めた画像：`hud-day-phone3x.jpg`・`hud-night-phone3x.jpg`・`hud-day-step-phone3x.jpg`（PC 用は `*-pc.jpg`、目盛り入りは `hud-day-grid-*`）。背景は 10/11 に撮った画面を引き伸ばしたもので、いまのアプリの HUD が写り込んでいる。

| 要素 | 1080p | スマホ幅での文字の大きさ | 明るさの比（明るい砂地の上、帯を含む） |
|---|---|---|---|
| 状態の1行 | 72px | 約14.6px | 7.0 |
| 視点の名前 | 56px | 約11.4px | 6.9 |
| 縄づくりの段階の並び | 48px | 約9.8px | 今の段階（黄）5.3、済んだ段階（青緑）4.9、まだの段階 5.5 |
| 島の時刻 | 48px | 約9.8px | 7.0 |
| AI の表記 | 40px | 約8.1px | 6.9 |

- 目で見た結果：状態の1行ははっきり読める。視点の名前・段階の並び・時刻は読めるが小さい。AI の表記は「あることが分かる」程度。
- **直した点**：帯の濃さを 55% → 62% に上げた（55% だと AI の表記が明るい砂地で比 4.3 で、目安の 4.5 を下回った）。まだの段階を薄くしすぎると比 3.3 まで下がるので、段階の区別は**色**（今＝黄、済み＝青緑、まだ＝白）と取り消し線で付け、薄さでは付けない。
- **置き場所の案を変えた**：AI の表記は右下ではなく**右上の時刻の下**へ。右下は YouTube の操作バーや進み具合の線と重なりやすく、状態の帯が長いときに帯とも近づくため。最終の位置は安全な範囲の撮影（§13-1）で決める。
- 縄づくりの段階の並びを出すと、左下の帯が画面の約15%を占める。ふだん（並びなし）は約11%。
- 縮めたときに読めるのは状態の1行が中心。ほかは「なんとなく分かる」大きさで、細かい情報は出さない方針と合わせている。
- 文字には薄い影か半透明の帯をつけ、昼の明るい砂浜でも夜でも読めるようにする。
- 「今」「あと○分」は使わない。時刻は島の時刻だけ。
- 置き場所は YouTube のプレーヤーの表示（題名・操作バー）と重ならない範囲で調整する。安全な範囲は要確認（§9）。

### 3-3. チャット

- 開く。住人には届かない（D4）。チャットの文は世界にも住人の AI にも渡さない。
- モデレーション（荒らし・個人情報）の方針と担当を決める必要がある。
- 見る人ができること：視点の投票（§6）、感想。できないこと：住人に話しかける、世界を変える。

### 3-4. 配信の基盤（main・本体の担当。ここでは要件だけ）

**開始時（D13）**
- 島は **1つだけ**。**自宅の GPU 付き PC が、世界と描画の両方を同じアプリで持つ**。
- **運用の前提：PC が止まると、配信だけでなく島も止まる。** 戻ったときは、閉じていた時間を最大12時間分、規則で追いつく（いまの追いつきの仕組み）。12時間を超えた分は追いつかない。
  - 追いつきの間は AI を使わず、規則（習慣）で暮らす。ログには「止まっていた」「規則で追いついた」区間として印を残す（§4）。
  - 見る人への伝え方（案）：配信が戻ったら、最初の数分だけ HUD の隅に「配信が止まっていた間の島は、規則で進めました」と出す。出すかどうかはオーナー判断。
  - 要確認（main）：いまの追いつきは、科学の工程の定期更新を通らない（ARCHITECTURE の既知の課題）。追いつきのあと、工程の状態が正しく続くか。
- 落ちたときは自動で再起動し、全画面で配信に戻る。
- 配信用の描画では、観賞用の早回し・季節・プリセットを使えない設定にし、住人を現実の時刻に固定する（main の「ライブモード」）。
- AI の予算台帳（月額1.5万円で必ず止まる）は、開始時はこの PC 側が持つ。

**開始後（G2 へ移したあと）**
- 共有の世界サーバー（G2、国内 VPS）が島を持ち、配信用の描画はそれを**読むだけ**。
- 描画が落ちても世界の時間は止めない。描画はすぐに復帰する。世界は保存と復旧ができる。
- 常時描画には GPU のある機械が要る（ソフトウェア描画では遅すぎることを 10/11 に確認）。
- 12時間を超える配信は YouTube にアーカイブされない（YouTube ヘルプ）ので、記録は §4 のログで持つ。

### 3-5. 夜の見どころ：見せ方の優先順位（案、2026-10-17）

行動の中身と判断は main が決める（D14）。ここは「映像としてどう見せたいか」だけ。

| 順位 | 場面 | なぜ | 見せ方 |
|---|---|---|---|
| 1 | **灯りをともす・灯りの番** | 夜の映像で一番強い。暗い浜に光が生まれる瞬間は、毎晩の見せ場で節目にもなる | 夕方の点灯は寄りで（灯皿と手元）、その後は引いて光の届く範囲と砂浜・ランタンを一緒に。灯りがあるあいだは、ランタンの視点の基本の構図にする |
| 2 | **星を見る** | 実在の星空（星座・天の川・惑星）がこのアプリの強み。住人と空を一緒に映せる | 低い位置から見上げ、ランタンの輪郭と星空を同じ画面に。月の明るい夜は海面の照り返しも |
| 3 | **夜の浜の探索** | 動く被写体がいると絵が止まらない | 後ろ斜め上から、進む先と足元が見える距離で。暗すぎる場所は避ける（灯りか月明かりのある所を選べるなら） |
| 4 | **気圧計を読む** | 映像としては小さく短い。ただ台風の知らせにつながる | 短い寄りの1カットで十分。状態の1行で意味を伝える。ダイジェストでは「台風の知らせ」の章に使う |
| 補 | **眠っている3人** | 静かな夜の絵として長く見ていられる | ラッコは水面に浮かんで眠る姿、カメマルは岩棚の寝場所、ドットは家の中か屋根の下。それぞれ1分ずつ |

- 夜の明るさ：月のない夜は暗くなりすぎるおそれがある。夜の露出（いまの「月明かりの見える夜」の描き方）で、ランタンの灯りと星が両方見えるかを、限定公開の試験配信で確かめる。
- 灯りとウミガメの利害（ロードマップ段階4、人工の光がカメの子を迷わせる）は、将来の夜の物語の候補。
- **自然班への依頼（案）**：灯りの光が、引いた画面でも届く範囲として見えること（明るさの値は世界から受け取り、見た目だけ）。

### 3-6. 日中の見どころ：殻と縄（案、2026-10-17、D17・D18）

行動の中身と判断は main、科学の中身は科学班、作業場の形と色は自然班。ここは見せ方と HUD の文言だけ。

#### 見どころの順位

| 順位 | 場面 | なぜ | 見せ方 |
|---|---|---|---|
| 1 | **縄を使った結果（もった／切れた）** | 一番の山場。丁寧さ（振るったかどうか）の違いが、ここで結果として見える | 筏を結ぶ・器を吊る場面は、縄が張るところまで引きで。**切れたときは切れた瞬間と、切れた縄の端が残る様子**を見せる。初めての縄・初めて切れた・初めて筏を結んだ、は節目の候補 |
| 2 | **縒り合わせる**（3本を1本に） | 1本の縄ができあがる瞬間で、形の変化が一番分かりやすい | 手元の寄り。3本が1本になっていくのが見える角度で |
| 3 | **撚る** | 繊維が糸になっていく変化 | 手元の寄り。糸が伸びていく長さの変化が見えること |
| 4 | **殻を打つ**（1個約4分） | 動きと音がある。ただし繰り返しになる | 最初は寄りで、手元・殻・打つ道具を同じ画面に。続くときは巡回で短くする（§3-1） |
| 5 | **浸ける・振るう** | 短い・地味な場面 | 振るうは、ごみや短い繊維が落ちる動きが見えれば1カット。浸けるは水に沈む殻が見えれば1カット |
| 補 | **繊維を乾かす**（屋根の下、島の暦で3日） | 待つだけの工程。住人は別の作業をしている | 島 13 の引きの画で、屋根の下の繊維の束が映る程度。乾きの変化は色で（自然班への依頼） |

#### 作業場の状態の HUD 文言（案）

科学側から届く作業場の状態（段階・作業中か・止まった理由・次の手順）を、表示の直前で言葉にする。世界や住人の AI には触れない、読み取り専用の写し。

**出す条件**：見ている住人の今の作業が、殻と縄の作業場の工程のとき（個別の視点）。島 13 の視点では出さない（開始時の最小構成。作業場が映っているかの判定が要るため、あとで足す）。

**出す場所**：状態の1行のすぐ上に、もう1行（48px、スマホ幅で約10px）。状態の1行より小さく。

| 作業場の状態 | 文言の型 | 例 |
|---|---|---|
| 作業中 | `縄づくり　浸ける・打つ・乾かす・振るう・撚る・縒る`（今の段階は黄色の太字、済んだ段階は青緑、まだの段階は白。薄さで区別しない：§3-2 のモック） | 「打つ」が黄色 |
| 省いた段階がある | 省いた段階は線で消す（取り消し線）。理由や影響（弱くなる等）は書かない | 「振るう」に取り消し線 |
| 待っている（乾かす） | `縄づくり　乾かしている（屋根の下）` | — |
| 止まっている | `縄づくり　止まっている：<理由>` | 止まっている：雨で乾かせない |
| 次の手順 | **出さない**（下の理由） | — |

- **「次の手順」を出さない理由**：段階の並び（浸ける→…→縒る）を見れば、次の段階は分かる。「次：振るう」と書くと、住人が振るうのを省いたときに画面と食い違い、住人の予定のように見えてしまう。並びは「この工程の順番」、住人が次に何をするかは住人が決める、と分けておく。
- **残り時間・乾燥の終わる時刻・何個目・何％は出さない**（D18）。「乾かしている」だけ。
- **止まった理由の言葉**は、科学側が返す理由の種類ごとに短い言葉を決める（例：雨で乾かせない／殻がない／道具がない）。理由の種類の一覧は**要確認（main・科学班）**。決まった言葉がない理由は「止まっている」だけにする。
- **隠れた値は出さない**：縄の強さ、キメ値、振るわないと弱くなる割合などは、HUD にも字幕にも出さない（D18）。見る人に分かるのは、どの段階を通ったかと、使ってもったか切れたかだけ。
- ダイジェストでは、同じ段階の並びを章の中の小見出しとして使ってよい（§5-1）。

#### 自然班・本体への依頼（どう映したいか）

| 宛先 | 依頼 |
|---|---|
| 自然班（形と色） | 打つ前と打ったあとで、殻の見た目が変わること（2〜3段階）。乾かしている繊維の束が、濡れているときと乾いたときで色が変わり、引きの画でも分かること。撚った糸・3本縒りの縄の太さの違い。切れた縄の端（ほつれ） |
| 自然班（形と色） | 作業場の屋根の下でも、手元が影で暗くなりすぎないこと（屋根の高さ・開き方か、明るさの扱い） |
| 本体（カメラ） | 作業の寄り：住人の斜め前45°・目の高さより少し上から、住人の体が画面の高さの約1/2〜2/3、**手元と対象（殻・糸・縄）が同じ画面**に入る構図。屋根の柱や棚で手元が隠れないこと（いまの構図の検査 `composition.cjs` の遮蔽の考え方を作業場にも） |
| 本体（カメラ） | 縄を使う場面：縄の両端（結んだ所と荷のかかる所）が画面に入る引き。切れた縄はその場で消さず、残す |
| 本体（記録） | 縄がもった／切れた、初めての縄、などを出来事として記録し（ログの L1・L3）、節目の札とダイジェストの「今日の節目」に使えるようにする |

## 4. 島のログ（記録と再現）

ライブを録画せず、**ログから島を再現する**（D5）。ダイジェスト・ショート・島だよりの写真・メンバーシップの再現視聴は、すべてこのログから作る。プロジェクトの原則「世界の事実と見た目を分ける」にそのまま沿う。

### 水準A（採用）：島の再現

| 記録するもの（案） | 粒度（案） |
|---|---|
| 住人の位置・向き・姿勢・持ち物・状態の文 | 数秒ごと（描画が間を補う） |
| 出来事（節目・ふだん）、会話（ルマウ語と訳）、日記 | 起きたとき |
| 工程の開始・状態の変化・結果 | 起きたとき |
| 天気（再生している記録の値）、島の時刻 | 定期 |
| 作った物・置いた物の出現・変化・消失 | 起きたとき |
| 写真を撮った瞬間（住人の写真）と、節目の瞬間のドロンの位置 | 起きたとき |

- 魚や鳥などの生態系は記録しない。描き直すたびに変わるので、再現の画面には「再現」と書く。
- 描画の版が変わると見た目も変わる。事実（ログ）は変わらない。
- コマ単位の完全な再現（水準B：乱数と AI の返答まですべて）はしない。

### main の形式案（2026-10-17）

3本の JSONL。容量は1日5MB前後、1年で約2GB の見込み。

| ファイル | 間隔 | 中身 |
|---|---|---|
| 姿勢 | 2秒ごと | 住人の ID、位置、向き、動作、持ち物、作業の種類、話している言葉の ID |
| 出来事 | 起きたとき | 出来事の通知、日記、会話、工程の状態の変化、天気（1時間ごと） |
| 島全体の写し | 1時間ごと | 保存データ全体を圧縮したもの |

入れないもの：API キー、AI への入出力の全文、チャット。

### 形式案へのコメント（ダイジェストと再現の視聴に足りるか）

方向は賛成。ダイジェスト・再現の視聴に使うために、次を足すか確かめてほしい。

| # | 足したいもの | なぜ | 重さ |
|---|---|---|---|
| L1 | **見える物の変化を、起きたときに出来事へ**（作った物の出現・置き場所の移動・消失、灯りの点灯と消灯、乾燥台の器、割れた器） | 1時間ごとの写しだけだと、19:10 に灯った灯りが再現で 20:00 まで出ない。夜の見せ場（§3-5 の1位）がずれる | 必須 |
| L2 | **状態の文（HUD の1行）を、変わったときに出来事へ** | ダイジェストの字幕や再現で、ライブで出ていた文と同じ文を出すため。動作と作業の種類から作り直すと、文の版が変わったときに食い違う | 必須 |
| L3 | **出来事の種類と節目の格**（`kind` と、節目かどうか） | ダイジェストの章立て、名場面の目次、ショートの選び出しがこれを使う（10/11 の 2-a） | 必須 |
| L4 | **止まっていた区間と、規則で追いついた区間の印**（始まりと終わりの時刻） | ダイジェストと再現が、その間を「規則で進んだ」と正しく扱うため（§3-4） | 必須 |
| L5 | **頭の向き（視線）と、作業の対象物の ID** | 住人の目線の再現（いまの pov の仕組み）と、カメラが手元と対象を一緒に撮るため | できれば |
| L6 | **高さ（水中の深さを含む）と、水中か陸か** | カメマル・ラッコの泳ぎと潜りの再現に要る。位置に高さが入っているなら不要 | 要確認 |
| L7 | **発話の始まりと終わり、話し手と聞き手、表示したルマウ語の文と訳** | 吹き出しの時刻合わせ。訳は後で変わりうるので、出した文を残す | できれば |
| L8 | **ライブで映していた視点の切り替え**（時刻と視点） | 「ライブで流れたあの瞬間」をショートや目次に使う。視聴の指標にも使える。容量はごく小さい | できれば |
| L9 | **各ファイルの先頭に、形式の版とアプリの版** | 描画の版が変わっても、古いログを正しく読むため | 必須 |
| L10 | 住人が写真を撮った瞬間の目の位置と向き | 島だよりの写真をログから描く（§7）。出来事の写真記録に入っているなら不要 | 要確認 |

- 天気が1時間ごとなのは、再生している観測記録が1時間ごとなので足りる。
- 容量は1年で約2GB に更新（10/16 の見込み1GB から）。§10-3 も直した。

## 5. 毎日のダイジェストとショート

### 5-1. 毎日のダイジェスト（15〜30分、自動公開）

ログから場面を選び、カメラを選んで**描き直す**。ライブの録画は使わない。

#### 章立てと場面の選び方（案、2026-10-17）

| 章 | 中身 | 場面の選び方（ログから） | 長さの目安 |
|---|---|---|---|
| 0. はじまり | 島暦の日付、その日の天気、朝の浜 | 天気の記録と、日の出のころの島 13 | 15〜30秒 |
| 1. 朝の集まり | その日の予定、天気の知らせ（ランタンの気圧計・カメマルのうねり） | 「朝の集まりが始まった」から終わりまで。発話はすべて残し、間の沈黙を詰める。台風で開かれなかった日は、その出来事の文を1枚で | 2〜5分 |
| 2. 日中のそれぞれ | 住人ごとの取り組み（縄づくりは段階の並びを小見出しに：§3-6） | 住人ごとに、状態が変わった所・工程の開始と結果・節目・写真・会話を拾う。歩いているだけの区間は最初の数秒だけ残す。住人の順は朝の集まりで話した順 | 1人2〜5分、合計12分まで |
| 3. 夜の焚き火の会 | 報告と情報の共有 | 「焚き火の会が始まった」から終わりまで。1 と同じ扱い | 2〜5分 |
| 4. 夜のランタン | 灯り・星・探索 | §3-5 の順位で。灯りをともした瞬間があれば必ず入れる | 2〜4分 |
| 5. 今日の節目 | その日の節目のまとめ | 節目の出来事の前後。なければこの章は作らない | 0〜2分 |

- **長さ**：目標は15〜30分。材料が少ない日は、景色で埋めずに短いまま出す（10分を下回ってもよいかはオーナー判断：§9）。
- **止まっていた区間**（§3-4）がある日は、その区間を描かず、説明欄に「○時〜○時は配信が止まり、島は規則で進んだ」と書く。
- **章の時刻**は説明欄に書く（YouTube の目次になる。最初の章が 0:00 から始まる必要がある等の決まりは要確認）。説明欄には島だよりのその日の記事への案内、「住人はAIです」、使用素材のクレジット（ピアノ音源 CC BY など）を書く。
- 題の型（案）：`<その日の一番の出来事> ｜ 島暦1年 6月3日 ｜ ルマウ`（例：「ランタンが初めて灯りをともした ｜ 島暦1年 6月3日 ｜ ルマウ」。末尾のシリーズ名は D23 で足した）。毎回同じ題にしない（YouTube の「量産」とみなされないため。§13 の Y5）。節目のない日は、その日の住人の取り組みから一つを題にする
- 字幕は会話（ルマウ語と訳）と出来事の文、状態の文だけ。住人の言葉は足さない・変えない。数字は世界が測ったものだけ。ナレーションは付けない。
- 公開の時刻は、島の一日（夜のランタンまで）が終わったあと、翌朝の早い時間（例 6:00 前後）。島だよりの毎日の実行と時刻をそろえるかは要相談。
- 描き直しは時間がかかる。同じ PC で描けるかは main が11月初めに測る（D10）。

#### 自動検査（公開を止める条件、案）

人の確認なしで公開する（D6）代わりに、次のどれかに引っかかったら**公開せずに非公開のまま残し、運営に知らせる**。知らせ方（メールか GitHub の issue か）は main が決める。

| # | 検査 | 中身 |
|---|---|---|

- 1回止まっても翌日の分は通常どおり作る。止まった回数は指標（§11「守り」）に数える。

## 13. YouTube の規約の確認結果（2026-10-17）

YouTube ヘルプと YouTube Data API の公式ページを読んで確かめた。公式に書かれていないことは「記載なし」とし、推測で埋めない。規約は変わるので、開始の前にもう一度確かめる。

| # | 項目 | 公式の記述（要点） | この設計への影響 |
|---|---|---|---|
| Y1 | 12時間を超える配信のアーカイブ | 日本語版：「12 時間を超える配信については、アーカイブは作成されません」。巻き戻し（DVR）も12時間を超えると使えない場合がある（[6247592](https://support.google.com/youtube/answer/6247592?hl=ja)、[9296823](https://support.google.com/youtube/answer/9296823)） | ログで残す方針（D5）のとおり。YouTube には残らない前提 |
| Y2 | 途切れたときの扱い | 自動停止をオンにすると、配信を止めてから約1分で配信が終わる（[API liveBroadcasts](https://developers.google.com/youtube/v3/live/docs/liveBroadcasts)）。同じストリームキーを使い続けるにはカスタムのキーを作る（[9854503](https://support.google.com/youtube/answer/9854503?hl=ja)）。自動停止をオフにしたとき、同じ配信（同じ URL）に何分まで戻れるかは**記載なし** | **自動停止はオフ、カスタムのキーで固定**。PC が長く止まったら配信が終わり URL が変わりうる。限定公開の試験で、何分止まっても同じ配信に戻れるかを実際に測る（§10） |
| Y3 | 推奨のビットレート | 1080p30：H.264 は最小5・推奨14 Mbps、H.265・AV1 は最小4・推奨10 Mbps。1080p60：H.264 は6／17、H.265・AV1 は4／12。キーフレームは2秒（[2853702](https://support.google.com/youtube/answer/2853702?hl=ja)） | **自宅の上り回線は、10/16 に書いた「10Mbps 程度」では足りない可能性**。1080p30・H.264 なら安定して15〜20Mbps 出るのが安心。H.265／AV1 が使える PC なら10Mbps台でもよい（§10-4 を更新） |
| Y4 | 遅延のモード | 通常：すべての画質と機能。低遅延：10秒未満、4K 不可。超低遅延：5秒未満、止まりやすく、字幕と1080p 超が使えない（[7444635](https://support.google.com/youtube/answer/7444635?hl=ja)） | **通常の遅延**でよい。チャットと映像の数十秒のずれは気にしない設計（HUD は島の時刻だけを出し「今」と書かない） |

### 13-1. main の受け入れ（2026-10-17）と、試験配信での撮影の手順

main が配信の運用の計画に入れたこと：自動停止オフとカスタムのストリームキー（落ちたら同じキーにつなぎ直す。5分・30分・2時間止めて同じ URL に戻るかを測る）、自宅 PC で H.264 14Mbps と H.265／AV1 10Mbps のどちらを安定して出せるかの実測、遅延は通常、11月中に新しいプロジェクトから上げた試験動画を公開に切り替えられるかの確認、ダイジェストの題名はその日の節目の出来事の文から毎回作る。試験配信の開始は11月中旬の目安。

**ダイジェストの題名の補足**
- 出来事の文が長いときは、最初の文（「。」まで）だけを使う。それでも長ければ、題名は出来事の文のまま、日付を後ろに回す。スマホの一覧で見える長さ（目安40字前後、要確認）を超える分は YouTube に任せ、こちらで切り詰めて意味を変えない。
- 節目のない日は、その日の出来事のうち、住人の取り組みの文を一つ使う（§5-1）。どれも住人の言葉は足さない。

**安全な範囲を決めるための撮影（試験配信の日に）**

| 端末 | 向き・表示 | 撮る状態 |
|---|---|---|
| PC（Chrome、1920×1080 の画面） | 通常の表示、シアターモード、全画面 | 何も触らない／マウスを乗せて操作バーが出た状態 |
| スマホ（iPhone と Android を1台ずつ） | 縦（アプリ内の小さい画面）、横の全画面 | 何も触らない／一度タップして操作が出た状態 |
| 埋め込み | Web ページに埋め込んだプレーヤー（幅 640px 前後） | 何も触らない／マウスを乗せた状態 |

- 画面には、試験用に**端から 5%・10% の位置に目盛りの線**と、§3-2 の文言表どおりの HUD を出しておく（目盛りは試験のときだけ）。
- この担当が画像を見て、題名・操作バー・チャンネル名などが重なる範囲を記録し、HUD の置き場所と文字の大きさを決める。
