# メモリに溜まる「ゴミ」の調査（2026-10-07、オーナー依頼）

アプリを長く使うと、メモリに使い終わったものが溜まり続ける仕組みがないかを調べた。実測とコードの読み込みの両方で見た。

## 実測（`tools/lab/memory.cjs`）

測り方：

- 1 ページで、描画はしない（GPU 命令を空にする）。
- 世界の時間を 1/20 s ずつ進める。
- 1 分ごとに不要なメモリを強制的に掃除（GC）してから、次を記録する。
  - JS ヒープの使用量
  - シーン内の物体・形状・素材・テクスチャの数
  - DOM 要素の数
  - レンダラーが持つ GPU 側の形状・テクスチャ・シェーダーの数（`seaglass.gpu()`）

| 場面 | 結果 |
|---|---|
| 宮古で巡航 15 分 | ヒープ 40.4 → 43.6 MB。後半 6 分は 43.2〜43.7 MB で横ばい。物体・形状・素材・テクスチャ・DOM の数は一定。 |
| めったにない光景を 10 回起こして終わらせる（宮古） | ヒープ 約 44 MB のまま。数も一定。 |
| 海の切り替え（下記） | 修正前：訪れた海は全部メモリに残る。1 海あたり JS で約 12〜18 MB、加えて GPU。 |

## 見つかったもの

### 直したもの

1. **地球儀で先に作って捨てた海が解放されていなかった**（`main.ts` `aheadStep`）。
   - 地球儀のカードを眺めると、その海を先に作り始める。訪れなかった海は一覧から消すだけで、3D データはシーンにつながったままだった。そのため二度と解放されなかった。
   - カードを眺めるたびに、1 海ぶん（JS 約 15 MB と GPU）が溜まっていた。
   - 直し方：シーンから外し、形状・素材・テクスチャを解放する（`freeOcean`）。
2. **訪れた海を全部持ち続けていた**（`oceans`、`lands`）。
   - 直し方：今いる海と、その前に訪れた 2 つ（`KEEP_SEAS`）だけを持つ。それより古い海は解放し、もう一度訪れたら作り直す。作り直す間は「海を用意しています」が出る。
   - 解放するとき、今いる海が使っている形状・素材・テクスチャは残す（共有されているものがある）。
   - 住人のいる海（島）は解放しない。住人の一日がその中にあるため。
3. **めったにない光景「シュモクザメの群れ」の素材**（`events.ts`）：終わるときに形状は解放していたが、群れのために作った素材を解放していなかった。
4. **SEA LOG の重複確認の記録**（`main.ts` `recent`）：出した文ごとに記録し、海を移るまで消していなかった。住人の行は毎回違う文になるので、島に長くいると増え続けた。90 s より古いものを消すようにした。

### 直していないもの（理由つき）

- **住人の物置の作り直し**（`robots/residents.ts` `drawStore`）：作り直すたびに古い形状・素材を解放していない。住人の作業（薪の追加など）のたびに少し溜まる。`src/robots/` は今回の担当外のため、直していない。
- **住人の記憶**（`robots/agent/agent.ts` `seen`）：見た物の ID を、物が「なくなった」と分かるまで持つ。物の ID は増える一方なので、ゆっくり増える。同じく担当外。
- **図鑑のサムネイル**（`ui/thumbs.ts`）：種ごとに 1 回だけ作る。上限が種の数なので放置した。
- **`?diag` の GPU 診断**：診断のときだけ使うので放置した。
- **小さい記録**（`capSeen`・`capNoted`・`sortShown`・`speciesKey`、`director` の `recent`・`skipUntil`・`watched`）：種名や対象の名前ごとに 1 つで、上限は「種の数 × 海の数」。数 KB 程度なので放置した。

### 溜まらないが、ゴミを多く出す所（参考）

- 住人の目線（カメマル）の表示中に、毎フレーム全部の被写体を作り直している（`main.ts` の POV 表示）。
- 監督が被写体の一覧を作るたびに、全部の被写体を作り直している（0.5〜3 秒ごと）。
- 小窓（PiP）の描画で、毎フレームいくつかのベクトルと配列を作っている。
- どれもメモリは増え続けない。ただ GC が頻繁に走り、遅い端末ではコマ落ちの原因になりうる。

## 修正後の確認（海の巡回：宮古 → GBR → モルディブ → 紅海 → 宮古 を 2 周、各 2 分）

| | 1 周目の宮古に戻った時 | 2 周目の宮古に戻った時 | 持っている海 |
|---|---|---|---|
| 修正前 | 113.7 MB | 114.5 MB | 4 つ全部（訪れた海は全部） |
| 修正後 | 96.9 MB | 97.7 MB | 3 つ（モルディブ・紅海・宮古） |

- 修正前は、訪れた海の数だけ増える。巡回では 4 海目までで止まった（シーンの物体 6867 個）。9 つの海を全部回れば、さらに 1 海あたり 12〜18 MB と GPU のぶん増える。隠れている海も、毎フレームの位置計算では全部たどられる。
- 修正後は、物体が 4998 個まで。

- 修正後は、海を 3 つ持った状態で JS ヒープが 97〜108 MB で頭打ちになった。もう 1 周しても増えない。
- GPU の形状の数も 1400〜2200 の間に収まった。
- ヒープのスナップショットで確かめた：解放した海（1 周目の宮古・GBR）は、もうどこからも参照されていない。

### 測定道具の落とし穴

- Playwright の `waitForFunction` は、最後に返した値への参照（ハンドル）を返す。条件の最後を `cur.eco`（海の生き物の仕組み）にしていたので、待つたびにその海がハンドル経由で生き残り、解放されないように見えた。
- 条件は `!!(…)` で真偽だけを返すようにした。アプリ本体の問題ではない。

## 引き換え

- 4 つ前以前に訪れた海へ戻ると、作り直しの間「海を用意しています」が出る（数秒）。直前の 2 つの海へ戻るときは、これまでどおりすぐ入れる。
- 島（住人のいる海）は数に入れず、いつでもすぐ戻れる。

## 追記：作っては捨てるゴミ（GC の負担）を減らした（2026-10-07）

- 測り方（`tools/lab/alloc.cjs`）：V8 の割り当てサンプリングで、60 s ぶんの動作中にどの関数が何 MB 作ったかを数える。描画はしない。関数名が読めるよう、圧縮しないビルドで測る。
- 修正前（宮古、巡航）：1 コマで約 3.3 MB を作っては捨てていた（60 s で 3.9 GB）。
  - 主な出どころは、魚の群れ・回遊群・ベイトボールの `update`（魚1匹ずつの計算）と `Math.hypot` で、合わせて約 7 割。
- 原因：
  1. **`Math.hypot` は呼ぶたびに引数の配列を作る**。魚1匹あたり毎フレーム十数回呼んでいた（全体で約 5 万匹）。
  2. **魚の `update` 関数は大きく、小さな関数を中に埋め込む（インライン化）上限を超える**。そのため、外の関数へ小数を渡す・受け取るたびに、数値を箱に入れていた（例：`shade.set(i, g, x, y, z)`、`lookAt`）。
- 直し方：
  - `hyp(a, b, c)`（`src/core/math.ts`、`Math.sqrt(a*a+b*b+c*c)`）に置き換えた。`src/robots/` 以外の 244 か所。
  - 魚1匹ずつのループ（fish・shoal・baitball・jacks）では、関数を呼ばずに式で直接書いた。
  - 群れの影の記録は、位置を配列と位置番号で渡す（`schoolShade.setFrom`）。
  - 回遊群の向きは、`lookAt` を呼ばず、軸を行列へ直接書く（ベイトボールと同じやり方。向きは同じ。スクショで確認）。
- 結果（Node で宮古の生態系を 3000 コマ、`--trace-gc`）：
  - 1 コマの処理：14.0 ms → 10.2 ms（約 28% 速い）。
  - 若い世代のゴミ掃除（スカベンジ）：1713 回 → 約 700 回（約 59% 減）。
  - ブラウザの割り当てサンプリング：1 コマ 3.3 MB → 1.2〜1.4 MB。
- 残り：地形の問い合わせ（`bommieField`・洞窟の `sd`・`T.top`）、three.js の描画準備、`for…of` の反復。どれも 1 つで全体の 1 割未満。
- 確認：水域・サンゴの深さ・水中経路・出現（宮古）のチェックは PASS。回遊群のスクショで、魚の向きが変わっていないことを確かめた。
