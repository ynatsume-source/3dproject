# 04｜継続するAI住民

## 1. 開発AIと住民AIは別

**開発AI**は、本人の依頼に基づいてコードやデータを作るClaude Code等。  
**住民AI**は、実行中の世界で限られた知覚と行動手段を持つキャラクター。

住民にコードの書き換え、シェル、任意URLへの通信、管理API、課金操作、秘密鍵へのアクセスを渡さない。「自由に暮らす」と「アプリの管理権限を持つ」を混同しない。

## 2. 住民の最小構成

| 要素 | 管理する内容 | 最初の実装 |
|---|---|---|
| 同一性 | ID、名前、登場した日時、身体ID | 固定の1体 |
| 個性 | 好奇心、警戒心、好み等 | 少数の明示パラメーター |
| 身体 | 居場所、移動能力、行動できる環境 | 既存モデル・移動方式を再利用 |
| 欲求と目標 | 休む、探索する、対象を観察する等 | 数種類で始める |
| 知覚 | 近くに見えるもの、聞いたこと | 読み取り専用の限定ビュー |
| 記憶と関係 | 実際の経験、相手への態度 | 少数の出来事から始める |
| 判断と行動 | 次の目標、実行中の行動、結果 | まずルール、後からLLM |

最初の1体は必ずしも人型でなくてよい。大切なのは「昨日の続きとして同じ個体に会えること」。現在のカメラガイドを使う場合も、各訪問者に付く案内役と、世界に1体だけ存在する住民を区別する。

## 3. 反射・生活・思考の3層

```text
速い反応：障害物回避、危険回避、姿勢制御
    ↑ 直ちに動ける。LLM応答を待たない
生活のルール：空腹なら食事、疲れたら休む、近所を巡回
    ↑ APIなしでも生活が続く
ときどきの思考：今日は何を調べるか、誰と話すか、出来事をどう受け止めるか
    ↑ LLMを使う候補。必要な場面だけ
```

魚の全個体を毎秒LLMに考えさせる必要はない。名前付きの重要な住民だけから始める。

## 4. 記憶は事実と解釈を分ける

世界が確定した出来事から、その住民が知覚できた分だけ経験記憶を作る。住民が見ていない捕食や、非公開の他人の情報は自動で知識に加えない。

記憶に持たせるもの：memoryId、住民ID、世界時刻、場所、相手、根拠イベントID、公開範囲、重要度、内容、記憶の種類。

- **経験**：実際に知覚した出来事。根拠にひも付ける。
- **要約・解釈**：経験をまとめたもの。「推測」であることを保持する。
- **信念**：キャラクターが信じていること。世界の事実とは別。

LLMが「私は以前ここで友人に会った」と生成しても、それだけで過去の世界履歴を追加しない。フィクションの記憶を導入する場合は、創作設定として明示する。

最初は直近・重要度・相手等で記憶を絞る。記憶量や検索品質が問題になるまでは、ベクトルDBを初期必須にしない。

## 5. AIへ渡すのは世界全部ではない

提案する入力：住民の個性、現在の欲求と目標、許可された行動、知覚中の対象、関連する少数の記憶、直近の行動結果。

提案する出力：候補から選んだ行動と引数、必要なら短い発話。デバッグ用には選択理由の短い説明を保持してもよいが、内部の長い思考を保存・公開する要件にはしない。

Anthropicのツール定義は入力スキーマを持てる。[S12] ただし形式に合う出力でも、実行可能・許可済み・安全とは限らない。世界側の検査は残す。

## 6. 行動の例と検査

LLMからの提案の概念例：

```json
{
  "decisionId": "decision-001",
  "actorId": "resident-001",
  "expectedPlanRevision": 4,
  "action": {
    "type": "observe",
    "targetId": "entity-020",
    "durationSeconds": 15
  }
}
```

これは実際のプロバイダーAPIのリクエスト形式ではない。アプリ内で扱う設計例。

世界側で検査するもの：認証された呼出元、対象の住民、許可された行動、引数の範囲、対象の存在、距離・移動可能性、期限、予算、同じdecisionIdの重複、計画の世代。

AIが考えている間も世界は進む。世界全体の更新番号が変わったという理由だけで全応答を失効させない。対象の有効性や、その住民の計画が既に差し替わったかを検査する。途中で危険回避に切り替えた場合は古い計画を破棄する。

失敗したら、無限に再試行せず、ルールによる行動へ戻す。

## 7. 接続先を交換するための約束

`BrainProvider.plan(context) -> proposal` のようなアプリ内の共通入口を持つ。ローカルのルール版とAPI版が同じ行動形式を返す。

保存・記録するもの：provider名、model識別子、プロンプト版、入力の版、採用した応答、適用tick、処理時間、利用量、検査結果。APIキーそのものは記録しない。

人格や記憶をAPIプロバイダー専用の会話ログだけに閉じ込めない。世界側に正本を持つ。モデルを替えても、既存の同一性と記憶を読み直せるようにする。

## 8. 費用と待ち時間

LLMは標準では無効。本人が費用上限と接続先を明示設定したら有効にする。初期は同時呼出1件等の小さな制約から試す。

費用管理は呼出回数だけでなく、入力・出力の利用量、モデル別の単価設定、予約中の処理を含める。料金は実装時点の公式情報を確認し、仕様に古い単価を固定しない。

呼出数の例：3体が1分に2回、2時間動くと `3 × 2 × 120 = 720回`。これは費用見積もりではなく、呼出頻度の設計例。

日次上限、最短呼出間隔、同時実行数、タイムアウト、有限回の再試行を設ける。世界時間を早回ししてもAPI利用制限の現実時間は早めない。

API停止、タイムアウト、予算到達時も、既存の計画やルールで世界は動く。UIには「高度な思考を一時停止」と出し、世界全体を止めない。

## 9. 公開・課金に進む前の境界

APIキーをブラウザ配布物へ含めない。公開エンドポイントには認証、本人の世界への操作権限、レート制限、費用上限を設ける。公開されるログと非公開の記憶を分ける。

ユーザーの会話、看板、住民の発話などは外部入力として扱い、開発者指示や管理権限に昇格させない。LLMの返答はUIで安全なテキストとして表示する。

課金ユーザーの「住民への関与」は、許された要求を出せる権限として後付けする。購入によって任意コードや世界データの直接編集を許す構造にしない。
