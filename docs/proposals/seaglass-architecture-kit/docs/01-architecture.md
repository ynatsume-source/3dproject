# 01｜世界設計と技術アーキテクチャ

## 1. どこまで決めるべきか

最初の機能ツリーは「何を作りたいか」の地図として十分。しかし長期開発では、さらに「誰が何を持ち、何を変更してよいか」が必要になる。

**今、具体化するもの：責任範囲、データの所有者、ID、単位、時間、保存、外部との接続、合格条件。**

**今、固定しないもの：全魚種の一覧、全大陸の地形、将来の経済制度、あらゆる行動、最終的なサーバー規模。**

機能の中身を細かく予言するより、後から差し込める約束を具体化する。

## 2. 長期の世界マップ

以下は論理的な機能区分。各行を別サービス・別フォルダとして今すぐ作る指示ではない。

```text
Seaglass
├─ World｜世界の基盤
│  ├─ Identity：世界・海域・個体のID
│  ├─ Geography：地形、水深、陸、洞窟、領域、座標
│  ├─ Time：正式な世界時間、季節、観賞用プレビュー
│  ├─ Environment：太陽、月、星、天候、潮、流れ、水温
│  └─ Lifecycle：生成、読み込み、退避、保存、復元
├─ Ecology｜生態系
│  ├─ Definitions：種、食性、生息条件、活動条件
│  ├─ Populations：群れ、個体数、移入・出生・死亡の方針
│  ├─ Bodies：位置、速度、体格、移動可能な環境
│  ├─ Behaviors：遊泳、群泳、回避、採餌、休息、捕食
│  └─ Events：誰が、いつ、どこで、何をしたか
├─ Residents｜継続するAI住民
│  ├─ Identity & Personality：名前、個性、価値観
│  ├─ Perception：その個体に見聞きできること
│  ├─ Memory：経験、要約、信念
│  ├─ Needs & Goals：欲求、目標、関係
│  └─ Brain & Actions：判断、実行、結果確認
├─ Presentation｜見せ方
│  ├─ Models & Materials：モデル、質感、魚体アニメーション
│  ├─ Lighting & Water：光、水面、かすみ、星、後処理
│  ├─ Audio：環境音、音楽、声
│  └─ Quality：画質、表示の詳細度、資産の読み込みと解放
├─ Visitors｜訪問者の体験
│  ├─ Observe：ドローン、視点移動、潜水、図鑑
│  ├─ Interact：話す、触れる、釣る等の操作要求
│  └─ Access：誰がどの操作をできるか
├─ Director & Media｜観察と配信
│  ├─ Interest：注目する出来事の選択
│  ├─ Camera：撮影位置、カメラ移動、追跡
│  └─ Recording：見どころの記録、録画、配信
└─ Operations｜維持する仕組み
   ├─ Persistence：保存、バックアップ、形式の移行
   ├─ Diagnostics：性能、エラー、AI費用、動作状況
   └─ Optional Services：ログイン、課金、住所・利用権
```

## 3. 最重要の分離：「世界の事実」と「見た目」

魚の位置・空腹・生存・住民の記憶は、世界側の事実。
魚のポリゴン数・尾びれの微振動・水の色補正・カメラの露出は、表示側の表現。

**表示を軽量化しても、その魚が別個体になったり、住民の記憶が消えたりしてはいけない。**

原則として描画は世界を読む。世界に変更を要求するものは、UIでもAIでも、明示されたコマンドの入口を通す。

これは「すべてのオブジェクトを毎フレームJSON化する」という意味ではない。描画用の配列・差分・読み取り専用ビューを使い、実装時に転送や割り当ての費用を測る。

## 4. 責任とデータの所有者

| 領域 | 自分が管理するもの | 参照するもの | 勝手に変更しないもの |
|---|---|---|---|
| 時間・環境 | 時計、天候入力、潮・光等の環境値 | 海域定義、外部データ | 個体の記憶、画質 |
| 地理 | 地形、水域、移動判定、海域・区画の境界 | 地形データ、生成設定 | 生物の目的、カメラの嗜好 |
| 生態系 | 個体・群れの身体状態、移動、生存、採餌等 | 環境、地形、行動要求 | レンダラー、LLM設定 |
| 住民 | 個性、記憶、関係、目標、計画 | 知覚可能な世界情報 | 物理状態への無検証の書き込み |
| 描画・音 | Mesh、材質、GPU資産、画面効果、音源 | 世界の公開ビュー | 正式な空腹・死亡・履歴 |
| 訪問者 | 入力、私的なカメラ状態、UI | 公開情報、操作権限 | サーバーの正式な世界状態 |
| 撮影監督 | 注目対象、画角、ショット計画 | 許可された出来事・公開状態 | 撮影のための捕食・天候の捏造 |
| 保存 | 保存・復元、形式検査、履歴の保持 | 各領域が出す保存用データ | 生態系の判断ロジック |
| 外部接続 | 天候API、LLM、認証等の呼び出し | 接続契約、予算 | 世界のルールの上書き |

`WorldState` は論理的な集合であり、全モジュールに渡して自由に書き換える巨大なグローバル変数ではない。各領域の状態に書き手を1つ定める。描画やAIには、必要な項目だけを渡す。

## 5. データの流れ

```text
静的な定義・保存データ ──→ 世界ランタイム
                                │
                                ├─ 公開ビュー ──→ 描画・音・UI・撮影監督
                                ├─ 限定した知覚 ─→ 住民の判断
                                └─ 保存用データ ─→ 保存アダプター

訪問者の入力 ─┐
住民の提案 ───┼─→ コマンド検査 ─→ 世界の更新 ─→ 確定した出来事
管理者の操作 ─┘
```

「サメを見つける → 逃げる目標を選ぶ → 移動システムが泳ぐ → カメラが追う」は別々の仕事。LLMが直接Meshの座標を書き換える構造にはしない。

## 6. 当面は1リポジトリ・1アプリ

提案するのは**モジュールを分けた単一アプリ**であり、最初からのマイクロサービス化ではない。

```text
src/
├─ main.ts             既存の入口。少しずつ接続・起動中心にする
├─ core/               既存の共通処理。内容を調査してから整理
├─ time/               既存を継続。時計の役割を明文化
├─ data/               既存を継続。定義データを段階的に分割
├─ eco/                既存の生態系を継続
├─ ocean/              既存のモデル・構築処理を継続
├─ render/             既存の描画処理を継続
├─ world/              必要になったとき、ID・状態・読み取り口を追加
├─ agents/             最初の永続住民を実装するときに追加
└─ infra/              保存や外部接続が必要になったときに追加

server/                共有世界や秘密のAPIキーが必要になる段階で追加
```

現在の `src/core/` 全体が描画非依存かどうかは未確認。新しい境界で非依存を守り、既存コードに突然厳格な制約を適用しない。

## 7. エンジンとAIを交換できる範囲

現在はThree.jsのWebGL描画が確認できている。[S2][S3] 本設計のためにReact、Unity、Unreal、WebGPUへ移行しない。

将来は描画側やAI接続側を比較しやすくする。ただし境界を作っても、シェーダーやアニメーションを別エンジンへ無変更で移せるわけではない。「移行が無料」ではなく「移行の影響を閉じ込める」ことが目的。

AIモデルの変更も接続先だけで完了としない。同じ知覚データ・行動形式に変換し、個性、コスト、待ち時間、失敗率を既存シナリオで評価してから採用する。

## 8. モジュールの説明に必要な粒度

各モジュールの設計は、次の8項目で始める。

**目的／管理する状態／入力／出力／更新タイミング／保存対象／触ってはいけない領域／合格条件。**

ファイル数やクラス数は先に決めない。変更理由や状態の所有者が違うところから分ける。
