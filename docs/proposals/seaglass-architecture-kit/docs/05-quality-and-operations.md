# 05｜品質・性能・保存事故・公開運用

## 1. まず現在の良さを固定する

既存の見た目を守る基準シーンを作る。場所・時刻・カメラ・画質・解像度を記録し、可能になったらseedと外部天候も固定する。

例：昼のサンゴ、夜の海、水面、洞窟、大きな群れ、陸のある海域。すべてを毎回手動チェックするのでなく、変更箇所に関係するものを選ぶ。

GPUやブラウザ差があるため、ピクセルの完全一致だけを成功条件にしない。比較画像、許容差、ちらつき・貫通・露出・旋回の観察項目を併用する。

## 2. 既存コマンドを起点にする

公開資料で確認できたコマンドは以下。[S1][S2]

```bash
npm run typecheck
npm run build
npm run sim -- miyako
npx tsx --import ./scripts/node-assets.mjs scripts/director-check.ts miyako
npx tsx --import ./scripts/node-assets.mjs scripts/clip-check.ts
```

この設計キットの作成時には実行していない。導入時に、現リポジトリに存在するか、何を確認し、失敗時に正しくエラーとなるかを調べる。単にログを出すスクリプトと、合否を判定する自動テストを区別する。

`npm test` 等の未確認コマンドを既存機能として報告しない。テストの追加は依存関係とともに小さな独立作業として行う。

## 3. 優先する自動検証

| 対象 | 合格条件の例 |
|---|---|
| 定義データ | 参照先が存在する、IDが重複しない、数値が範囲内 |
| 時間 | fpsを変えても正式な経過・同一入力の判断が許容範囲で一致 |
| 個体 | NaNの位置、禁止区域への移動、二重の捕食確定が起きない |
| 保存 | 同一住民・目標・記憶が復元できる。未対応形式は安全に拒否 |
| AI | 未知の行動、期限切れ、重複、消えた対象、API停止を扱える |
| 境界 | 新しい世界契約がDOMや描画実装へ不要に依存しない |
| 共有 | 2台が同じ確定イベントを観察する。再接続で再同期できる |

描画・乱数・外部APIを含む全体の完全再現は保証しない。まずルール側のテストを、同一の実行条件・固定入力・記録済みAI応答で再現可能にする。

## 4. 性能は基準機とシーンをセットで扱う

暫定の目標例：本人の主力PC・1080p・標準設定で60fps、軽量端末では30fps。これは測定前の目標であり、今のアプリや特定GPUで達成済みという意味ではない。

記録するもの：端末、GPU、ブラウザ、解像度、品質設定、海域、個体数、平均とp95フレーム時間、長い停止、CPU処理時間、描画呼出数、資産数、通信量。

60fpsの1フレームは約16.7ms、30fpsなら約33.3ms。平均値だけでなく、時々引っかかることを確認する。CPU計算とGPU描画のどちらが詰まるかを分ける。

ブラウザ内の資産数や見積もり容量を、そのままPC全体の正確なVRAM使用量と説明しない。

## 5. 長く眺められることを品質にする

最初は30分程度の連続観察、次に海域の往復や保存再開、常時運転段階で長時間の試験へ進む。

確認項目：資産やイベントログの無制限増加、未完了AIジョブの蓄積、地域切替後の不要な描画資産、音源の重複、タブ復帰時の巨大な時間ジャンプ、再接続時の二重処理。

GPU資産の解放は、共有しているgeometry/textureを他の地域が使っていないかも確認して行う。[S9][S10]

## 6. 画質を下げる場合の順序

解像度・後処理・遠景の細かさ・装飾密度等を候補にし、必要なら計算対象数を制限する。ただし正式な世界に存在する名前付き住民を「軽量化のため消滅」させない。

GPUの表示詳細度と、世界のシミュレーション詳細度は別設定。画面を遠くへ向けたせいで住民の人生がリセットされる構造を避ける。

## 7. 保存と更新の事故を防ぐ

保存形式・生成器・コンテンツの版は分ける。新コードの起動時に、旧データへどう対応するかを判定する。

移行は元ファイルを保持した上で行い、失敗したら復元可能にする。単純なコードの巻き戻しが新形式のセーブを読めるとは仮定しない。更新前バックアップと復旧手順をセットにする。

初期のローカル保存にも、エクスポートと復元の試験を持たせる。クラウド移行時にはバックアップが「ある」だけでなく「戻せる」ことを確認する。

## 8. 撮影と世界の進行を分ける

撮影監督は、世界の公開イベントから見どころを選ぶ。映像を盛り上げるために住民の行動や過去の出来事を勝手に書き換えない。

演出する機能を作る場合は、観測とは別の管理操作として表示・記録する。見どころにはworldId、世界時刻、場所、関係する個体IDを残す。

イベントの記録だけでは、過去の映像を必ず再現できるとは限らない。録画そのものを残すか、再現に必要な世界状態と入力を残すかを分けて設計する。

常時配信を始める時には、描画停止検知、再起動、無音・黒画面、公開してよい会話、音源・画像の利用条件を確認する。配信先の最新規約や具体的な収益化可否はその段階で別途検証する。

## 9. 商用化のために今残す接続点

今用意するのは、安定したID、公開・非公開の情報区分、権限を検査する操作入口、資産の出典台帳、出来事の記録まで。

商品、決済、月額プラン、住民への関与ルール、土地や住所の権利モデルは未確定のまま残す。土地を販売することと、内部で場所のIDを付けることは別問題。法的・運用上の条件を決めずに権利を発行しない。
