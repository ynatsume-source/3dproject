# 06｜実装ロードマップ：期間ではなく到達点で進める

## 方針

構想全体の完成を最初の目標にしない。見た目を磨く楽しさと、少しずつ信頼できる基盤を作る作業を並行する。大規模リファクタリングだけの期間を長く作らない。

## Stage 0｜現状の良さを守る

**体験：今の海が、整理のせいで壊れない。**

公開コードとローカルの差を確認し、現在のコミット、実行できる検証、基準シーンを記録する。既存の責任分担と、変更が集中する箇所を地図にする。

完了条件：typecheck/build等の結果、既存の失敗、未確認事項が分かれている。最初の小さな変更範囲と戻し方が明確。

今しないこと：依存関係更新、全面的なフォルダ移動、新エンジン、商用機能。

## Stage 1｜同じ住民に再会する

**体験：1つの海域にいる1体が、再読み込み後も前の続きを持っている。**

固定IDを持つ住民を1体、実験用の小さな範囲に追加する。外見は既存資産の再利用でよい。行動は探索・観察・休息程度。LLMなしで個性パラメーター、少数の経験記憶、保存復元を作る。

Scenicモードは保ち、Local habitatの実験を明示的に分ける。新しい住民だけを保存する初期段階では、既存の全魚群が永続化したとは扱わない。

完了条件：名前・ID・目標・記憶が保存され、再開後も続く。見た目を替えても同一性が残る。保存エラーが見える。

## Stage 2｜住民が少し意外な判断をする

**体験：同じ個体が、経験や好みに応じて次の行動を選ぶ。**

ルール版BrainProviderにAPI版を追加する。最初は1体・少数の行動・短い知覚・少数の記憶。APIキーを保持できる開発用バックエンドを用意し、公開前は本人だけが使える入口にする。

完了条件：APIなしでも生活が続く。存在しない対象や不正な行動を拒否できる。費用上限・待ち時間・失敗率が見える。同じテストでモデルを比較できる。

ここでは必ずしも24時間稼働や多人数共有を導入しない。

## Stage 3｜本人が見ていなくても同じ世界が続く

**体験：ブラウザを閉じても進み、別の端末から同じ住民に会える。**

常駐する世界プロセスを導入し、時計と正式状態をサーバー側へ移す。最初は単一世界・単一書き手。定義・状態・描画の境界を使い、全画面をサーバーへ移すのではなく状態だけを同期する。

完了条件：再起動からの復元、2クライアントの一致、切断からの再同期、バックアップ復元、停止状態の表示を検証できる。

常時稼働の費用を払う価値を感じたときに着手する。

## Stage 4｜土地・体験・観察者を増やす

**体験：海から陸へ移動し、複数の住民を観察し、遊びに関わる。**

地域の読み込みと計算詳細度、住民の関係、訪問者の許可された操作を必要なものから追加する。撮影監督を使って見どころを保存し、配信を別工程として試す。

完了条件：地域を往復しても個体・記憶が失われず、負荷に上限がある。観察者が増えても世界の更新を重複実行しない。

## Deferred｜必要が生まれるまで作らない

全地球の連続ストリーミング、巨大な物理エンジン、全魚のLLM化、独自基盤モデルの学習、最初からのベクトルDB、マイクロサービス、Kubernetes、土地販売、決済、NFT等。

将来使わないという判断ではない。今の楽しさ・検証・継続性に必要でなければ後回しにする。

## 次の作業を選ぶ判断軸

「この変更で見たり遊んだりする喜びが増えるか」「次の変更を安全にするか」のどちらかが説明できる作業を選ぶ。

構造変更は1回に1つの理由で行う。魚を増やす作業のついでに時計・保存・描画エンジンを入れ替えない。
