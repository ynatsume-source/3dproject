# 02｜世界のID・時間・更新・保存

以下の値や方式は初期提案。現コードへの適用前に基準動作と差分を確認する。

## 1. 世界を識別する

| ID | 意味 | 例 |
|---|---|---|
| worldId | どの世界・セーブか | seaglass-local-001 |
| regionId | どの海域・島・地域か | miyako |
| cellId | 読み込み・計算の区画 | miyako:0:1 |
| entityId | 同じ個体であることを示す | resident-001 |
| definitionId | 種や住民の設定の参照先 | resident.guide.v1 |
| assetId | 見た目や音の資産の参照先 | model.guide.default |

例の文字列は設計例であり、既存のID規則を勝手に置き換えない。

名前は変えられてもentityIdは同じ。海域間の移動やLOD切替でも変わらない。外見が同じでも、別個体なら別ID。

重要な住民は最初から永続IDを付ける。装飾用の小魚全部に長期記憶を持たせる必要はない。採用する個体化の段階を明示する。

## 2. 座標と単位

新しい永続領域の共通ルール案：距離m、時間s、速度m/s、角度rad、日時UTCのミリ秒。緯度経度は地域の参照位置として扱う。

地域内の座標はメートルの局所座標。案として右手系のx=東、y=上、z=南を採用できるが、**現コードの方位との照合が先**。既存のzを無確認で反転させない。変換は1箇所のアダプターが担当する。

惑星全体の位置を、そのまま巨大な描画座標として全オブジェクトへ渡さない。地域を読み込む方式から始め、必要なときだけ局所原点の移動・区画ストリーミングを導入する。

地形の問い合わせは、将来的には `sampleTerrain(position) -> { heightM, waterDepthM, substrate, reefCover }` のような戻り値へ整理する。既存の地形関数は海域定義にあり、共有の地形補助値との関係があるため、まずラッパーで動作を保つ。[S4]

## 3. 3つのモードを混ぜない

| モード | 意図 | 時間と保存 | 誰と共有するか |
|---|---|---|---|
| Scenic：現在の観賞体験 | 今の海、夜景、季節を自由に眺める | 現行挙動を維持。照明・活動リズムの変更を許す | 原則各ブラウザ独立 |
| Local habitat：最初の住民実験 | 同じ住民に再会する | 正式な世界時間と保存を持つ。閉じた間は初期版では停止 | 本人のローカル世界 |
| Shared habitat：将来 | 複数人が同じ住民の暮らしを見る | サーバーが時計と正式状態を持つ | 同じworldIdに参加した人 |

**夜景を見たい操作で、共有世界の住民を急に老化させない。**

共有世界では、見た目だけ変えるプレビューは正史を書き換えない。環境も含めた実験は別worldIdの複製世界で行う。プレビューであることをUIに表示する。

既存READMEは、移動の速さを実時間、活動リズムをシミュレーション時計として説明している。[S1] この挙動を永続世界の導入と同時に一括変更しない。

## 4. 正式な世界の時計

Local/Shared habitatでは、初期は世界時間1倍を推奨する。固定の短い更新単位を積み上げて世界の経過を管理する。

分けるもの：

- `worldTime`：住民の経験、空腹、出来事の日時に使う正式時間。
- `presentationTime`：観賞用の空や照明を試す時間。明示したプレビューだけ。
- `wallTime`：APIの待ち時間、予算、通信制限、現実のデータ取得時刻。

高速テストは、大きすぎるdtを渡すのではなく通常の小さな更新を多数実行する。実際の天体日時へ対応させる場合はepochを保存する。速度変更や時刻ジャンプは世界の管理操作として記録し、日常の視点操作とは分ける。

Local habitatでは閉じた時間を勝手に全量再計算しない。再開時に現実時刻へ強制追従もしない。将来のオフライン進行は「簡略進行」「停止」「常時サーバー」のいずれかを別仕様として採択する。

## 5. 更新頻度は仕事ごとに変える

| 仕事 | 初期の候補 | 注意 |
|---|---|---|
| 描画・見た目の補間 | 画面更新に合わせる。目標60fps等 | 性能目標であり保証ではない |
| 移動・接触等 | 20Hz程度から測定 | 速い物体・接触精度に応じて変更 |
| 欲求・簡単な行動判断 | 1Hz程度から測定 | 緊急回避は別の速い反応へ |
| LLMによる計画 | 必要なイベント時だけ | 毎フレーム・毎tick呼ばない |
| 遠隔地域の概略進行 | 低頻度、または一時停止 | 地域の継続性に応じて採択 |
| 天候API | キャッシュと取得上限を使う | 提供元の条件・更新頻度を確認 |

速度・品質の数値は実測前の仮説。魚数やPC性能に無関係に固定できる最適値ではない。

## 6. 1回の世界更新

1. 現tickに適用する入力、完了済みAI応答、外部環境データを取り込む。
2. 期限・権限・対象の存在・重複・実行可能性を検査する。
3. 同じ更新開始時点の状態を使って、知覚・環境・行動を計算する。
4. 移動・接触・採餌・捕食などの競合を所定の順序で解決する。
5. 次状態と、確定した出来事を記録する。
6. 必要なら次のAI計画を非同期で予約する。ここで通信完了を待たない。
7. 描画、UI、保存へ必要な読み取りビューを渡す。

並行する提案の結果を、JavaScript Promiseが偶然返った順だけで決めない。受け取った応答の適用tickや結果を記録する。

## 7. 地球規模へ広げる方法

「世界が広い」ことと「全領域を常時高精細で計算する」ことを分ける。

**描画の詳細度**：近くは細かいモデル、遠くは簡単なモデルや非表示。  
**シミュレーションの詳細度**：重要な近隣個体は詳細、遠方の群れは集団の概略状態。

遠方を簡略化しても、名前付き住民のID、重要な記憶、所持品等を失わない。個体から集団にまとめてから戻す場合には、個体数や履歴の扱いを別途定義する。

最初は1海域、次は既存の海域切替。連続した陸海の区画読み込みは、その移動体験が必要になってから。区画サイズは実測して選ぶため、今は固定しない。

共有世界の計算範囲はサーバーが管理する。観客が増えるたび、各ブラウザが同じ捕食や個体生成を正式状態へ重複適用してはいけない。

## 8. 定義と保存の分離

保存する候補：世界ID、世界時刻、住民ID、位置、欲求、目標、行動途中の状態、重要な記憶、関係、世界の変更差分、乱数状態、コンテンツ版。

保存しないもの：Mesh、Material、DOM、GPUテクスチャ、API秘密鍵、関数そのもの。これらはIDから再構築する。

```text
保存ヘッダー
├─ schemaVersion：保存形式
├─ contentVersion：種・地形・ルールの内容の版
├─ generatorVersion：生成アルゴリズムの版
├─ worldId / seed / worldTick / worldTime
├─ lastEventSequence
└─ 実際の保存日時（wallTime）

保存本体
├─ 個体・住民の状態
├─ 計画・実行中行動
├─ 記憶と関係
├─ 地域・個体群の変更差分
└─ 再開に必要な乱数・スケジューラ状態
```

seedだけでは再現性を保証しない。生成器やデータの版、乱数の消費順、実際に採用した外部入力も影響する。地形生成と見た目の揺らぎで乱数系列を分ける。

## 9. 保存の導入順

初期の候補はブラウザのIndexedDBと、手動エクスポート／インポート。IndexedDBはブラウザ側の構造化データ用ストレージであり、クラウドバックアップではない。[S8]

保存形式を持つ最小の住民から始める。**その段階では既存の全魚群まで永続化したとは説明しない。** 保存対象をUIと文書に明記する。

保存に関する合格条件：

- 保存→再読込で同じ住民に再会できる。
- 保存処理が失敗した場合は、成功したように見せない。
- 旧セーブはバックアップしてから移行する。
- 未対応の新形式は、黙って初期化せず読み込みを拒否する。
- 正式状態と対応する出来事の位置を、矛盾のない組で保存する。
- 多重タブの同時書き込みは、初期版では単一の編集セッションに制限する。

全イベントを無制限に保存する必要はない。診断用ログ、住民の重要な記憶、録画素材を分け、それぞれ保持上限を設ける。

## 10. 「誰も見ていなくても暮らす」を追加するとき

ブラウザの描画ループは非表示タブ等で停止する場合がある。GitHub Pagesは静的ホスティングである。[S6][S7] 現在の公開方法だけを、常時稼働の世界シミュレーターと見なさない。

その体験を必要とする段階で、正式な世界を更新する常駐プロセスと永続ストレージを導入する。最初は世界1つにつき書き手1つを推奨。

```text
常駐する世界プロセス（正式な状態）
├─ シミュレーション
├─ 保存・復元
├─ 住民のAIジョブ
└─ 公開用スナップショット／差分
      ├─ 本人のブラウザ
      ├─ 観客のブラウザ
      └─ 録画・配信用ブラウザ
```

通信の初期契約は、接続時のスナップショット＋順序番号付き差分＋再同期。クライアントが状態変更結果を直接保存するのではなく、操作要求を送る。サーバー停止時には停止中と表示し、クライアントを勝手に別の正式世界へ昇格させない。

常時世界と常時映像配信は別。世界の状態だけなら画面を描かずに進める設計にできる。映像を出すには別途描画・キャプチャ・配信処理が必要になる。
