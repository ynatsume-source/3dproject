# 07｜AIが長く開発できる文書と作業の仕組み

## 1. 会話履歴を設計の正本にしない

世界の方針・変更してはいけないこと・検証方法をリポジトリへ残す。新しい会話や別のAIでも、その作業に必要な情報だけで着手できるようにする。

ただし、文書を増やすだけで安全になるわけではない。正式ルール、未採用の提案、現コードの事実を区別する。

## 2. 常に読む文書は短く、詳細は必要なときだけ

Claude Codeの公式資料はCLAUDE.mdをプロジェクトの指示として説明し、簡潔で具体的な記述を推奨している。また厳密な遵守の保証ではないと明記している。[S13]

提案：CLAUDE.mdには目的、変更の制約、既存コマンド、必要な文書への道案内だけを書く。魚の作業では魚の仕様、AIの作業ではAIの仕様を追加で読む。全設計書を常に自動インポートする運用にしない。

同梱の `CLAUDE.md.proposed` は導入候補。元の指示と衝突しないか確認し、採用した決定だけを正式化する。

## 3. 最小限の文書セット

| 文書 | 役割 | 更新する場面 |
|---|---|---|
| CLAUDE.md | 毎回の道案内・共通制約 | 共通作業ルールが変わるとき |
| Architecture | 所有者・依存・データの流れ | 境界が変わるとき |
| Domain spec | 時間、魚、住民等の仕様 | その領域の仕様が変わるとき |
| ADR | なぜ選んだか、再検討する条件 | 後戻りの費用が大きい判断時 |
| Task | 今回の目的・範囲・合格条件 | 作業ごと |
| Status | 実装済み、途中、既知の問題 | 作業の終了時 |

ADRはArchitecture Decision Recordの略。複雑な形式ではなく、状況・選択・理由・欠点・見直す条件を短く残す。

## 4. 毎回の仕事に必要な項目

目的、変更する領域、変更しない領域、関連仕様、入力条件、期待する振る舞い、性能への影響、検証、保存互換性、戻し方。

設計を大きくするより、作業を小さくする。

例：

> 夜の魚群が急に方向転換しないようにする。見た目の姿勢補間だけを対象とし、個体数・泳ぐ速度・捕食判定・世界時計は変えない。昼と夜の同じカメラで比較動画を示す。

これなら、AIが成功のために他の世界ルールまで変更する余地を減らせる。

## 5. 作業の順序

最初に現在のコードと関連仕様を読む。変更前の検証を実行できる範囲で記録する。変更点と影響を短く整理し、発注範囲内の小さな変更を実装する。検証と差分確認を行い、文書・状態を更新する。

未依頼の有料API実行、依存関係の大幅更新、公開push、保存データ削除、共有世界の破壊的変更は行わない。必要性が判明したら別タスクにする。

変更しなかったことや、未検証のことも報告する。「問題ありません」だけで終わらせない。

## 6. 守るべきことは機械にも確認させる

指示文だけではなく、型検査、入力検査、単体テスト、保存復元テスト、可能になったら依存境界の静的検査やCIへ落とし込む。

「renderから世界状態を書き換えない」という約束は、読み取り用インターフェースや限定した書き込み口で支える。ただしTypeScriptの型だけをセキュリティ境界と見なさない。外部データには実行時の検査を行う。

描画の改善には基準画像・短い動画を使う。「自然になった」の評価は、本人が重視する観察条件と結び付ける。

## 7. 複数AIで並行開発するとき

初期は1つの統合作業者を中心にする。並行させるなら、触るファイル・公開インターフェース・共通定義の変更担当を明示する。時計や共通型を複数のAIに同時編集させない。

統合前に実際の差分とテストを見る。別々に成功した変更が、合わせても成功するとは仮定しない。

## 8. AI能力の進歩への備え

接続先を替えられること、記憶や世界状態を標準的なデータとして保持すること、同じ評価シナリオを残すことが重要。

将来のモデルが賢くなっても、目的・過去の判断・壊してはいけない制約が不明なら、望む開発とは一致しない。逆に、今のAIで検証できる小さな仕事に分けておけば、モデルが変わっても改善を継続しやすい。

この構造は大規模化や無人開発を保証するものではない。失敗を局所化し、評価と復元をしやすくする設計である。
