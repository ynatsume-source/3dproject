# 70fed2f の軽い確認：0.2.0 採択時の互換性

2026-10-04。科学側 `70fed2f8dec477daa72f04fe43a779b98afa8e9d`。
オーナーの `REVIEW_POLICY.md` に従い、契約の受付・応答と0.2.0採択後の整合に絞って確認しました。

**依頼にあった影響B（採択で秤量・成形だけ対応版が切り替わる）は解消しています。**
ただし、今回0.2.x対応を表明した秤量・成形に、0.2.0案の均一なエネルギー供給と整合しない点が1件あります（影響A）。

## A1 — 秤量・成形が、区間後半に届くはずのエネルギーを前半で使う

影響 **A（届いていないエネルギーで工程が先に完了し、世界の時刻と結果が食い違う）**。
該当: `src/science/step/simple.ts:123–129`。新しい受付判定は同ファイル37–43行付近。

0.2.0案の `EnergyOffer` は `maxJ` が要求区間全体へ均等に届く、と明記しています。
`simple.ts` は区間全体の `maxJ` を先に使える仕事量として `floor(maxJ / power)` 秒へ変え、
`simulated.to = from + seconds * 1000` に短縮して完了します。
したがって、要求が工程時間より長く供給電力が不足する場合、報告した時刻までに届いていないJを使用します。

| contract 0.2.0 の要求 | 実際の返答 | 返答時刻までに届く量 |
|---|---|---|
| 秤量 `[0,30000) ms`、電力の申し出10 J | `completed`、`simulated.to:10000`、使用10 J、測定時刻10000 ms | 10 × 10/30 = **約3.33 J** |
| 成形 `[0,120000) ms`、機械仕事の申し出120 J | `completed`、`simulated.to:60000`、使用120 J、試験片生成 | 120 × 60/120 = **60 J** |

どちらも通常の整数秒・30秒境界の要求で、検査器の違反は0です。
現行の `validateResult` が比較するのは区間全体の `maxJ` なので、区間途中での先取りは検出できません。
提案未適用の70fed2fと、提案を適用して `SCIENCE_CONTRACT_VERSION='0.2.0'` にしたコピーの両方で同じ結果でした。

この計算式は旧版由来ですが、今回新しく受け付ける0.2.xの供給規則に合わせる部分が未対応です。
**修正依頼:** 要求区間に均等に届く供給量・電力を上限として、進捗・完了時刻・使用Jを整合させてください。
不足時の動作は科学側で定義し、将来届くJを使って先に完了することがないようにしてください。

**回帰の補足:** 「contractとdrawn以外が同じ」は形式互換の検査として有効です。
一方、同じ計算を両版で行えば、この問題があっても一致します。
上の長い要求・不足供給を使い、報告した完了時刻までに届くJと実際の使用Jを比較する検査を追加してください。
0.1.xとの完全一致を保証する範囲も、採択後の規則と合わせて整理してください。

## 修正を確認できたこと

- 科学側の6系統の比較回帰は成功。乾燥・電気窯・石灰の焼成・消化・浸漬・秤量で、検査した区間の応答はcontractとdrawn以外が一致。
- 追加で秤量・器の成形・試験片の成形を確認。成功、進行中、エネルギー不足、中断、不正入力の拒否を含む7ケースについて、`0.1.0 / 0.2.0 / 0.1.7 / 0.2.7` の応答本体が一致。
- 上記は定数が0.1.0の原本・0.2.0の採択コピーの両方で成功。定数変更による受付の切り替わりはなくなった。
- 成形の0.1.0の進行状態をJSON往復し、次の区間を0.2.0で渡しても、0.1.0で続けた場合と同じ完了結果。
- 10入口×2契約版の不正工程版・未知工程の20拒否は、contractを維持。0.2.0だけ `drawn:[]` を付け、すべて検査器違反0。
- `drawn?` は型での両立のための省略可で、実行時の規則は維持。正常応答から0.2.0のdrawnを削除する変異と、0.1.0へdrawnを追加する変異は、どちらも検査器が拒否。
- 薪は引き続き0.2.x専用。薪専用検査の0.1.0拒否も成功。
